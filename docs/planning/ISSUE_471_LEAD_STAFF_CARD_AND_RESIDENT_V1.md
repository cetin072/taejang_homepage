# Issue #471 — 운영팀장 전체 직원관리 단일 화면 / 주민번호 제한권한

상태: 2026-10-16 사용자 수정 승인. 코드와 격리 검증만 진행하며, 운영 DB migration 및 Production 배포는 별도 릴리스 승인 대상.

## 업무 목표

- 기존 **직원관리 → 직원 목록 → 직원 한 명 인사카드**를 유일한 관리 화면으로 사용한다.
- 운영팀장(`promotion_lead`)은 부서가 달라도 모든 비보관 직원의 **기본 명부**(이름·직원번호·입사일·부서·직책·근태대상·앱 연결 여부·업무용 얼굴사진)를 조회한다. 기본 필터는 재직·휴직, 전체 필터에서 퇴직자를 구분하여 하단 표시한다.
- 기존 별도 `직원 현장 전수조사` 버튼/로드는 제거하고 설치 확인·인적사항 체크를 직원카드의 앱 계정 주변에 통합한다. 실제 앱 설치 여부는 현장 점검 기록이며, 계정 연결/출퇴근 이력/푸시토큰만으로 설치 완료 판단 금지.
- 운영팀장은 보호·임원·고권한 직원 외의 비보관 일반 직원만 기본정보 직접 교정한다. `update_employee_field_audit_basic` 서버 가드 및 최신 `updated_at` 검사 재사용. 그 외 수정은 운영총괄 담당.
- 업무용 직원 얼굴사진은 기존 비공개 `employee-private-media/{employee_uuid}/profile` 사용. 민감한 `id_photo` 직접 관리권한 확대 금지.

## 주민등록번호 업무와 급여 권한의 분리

장애인 고용 지원사업 및 인사·법정 고용 행정의 개별 확인 필요성을 위한 최소 기능.

- 기존 `set_employee_resident_registration_number` 함수의 Vault 암호화, 유효성검사, 중복번호 차단, 감사 기록을 재사용한다.
- 운영팀장에게 별도 `employee.resident_number_manage` capability만 부여한다. 실제 운영팀장 또는 운영총괄 역할까지 서버에서 대조하고, 운영팀장은 CEO/운영총괄 등의 보호 계정 주민번호 등록·열람 금지.
- 직원카드는 평상시에 **주민번호 등록됨/미등록**만 표시. 필요 시 단일 직원에 대해 목적(지원사업/입사 인사 대조)을 선택해 열람하며 감사 로그에 직원 UUID·조회자·목적을 남기되 **번호 원문은 감사·기록·명부에 남기지 않는다**.
- 일시적으로 화면에 보인 번호는 직접 숨기기 또는 30초 후 자동 숨기기. URL, localStorage, sessionStorage, 일괄 API, 파일/CSV, 콘솔로그 등에 주민번호 원문 사용 금지.
- **급여 및 보험 공제·4대보험 요율 결정/수정 권한은 절대 확대하지 않는다.** `employee.sensitive_identity_manage` 같이 급여 보험 예외를 포함한 넓은 권한도 운영팀장에게 주지 않는다. 직원 명부/변경 요청에도 급여 데이터 노출 금지.
- 직원번호·기존 급여·출퇴근 원장·로그인/Auth 계정은 변경하거나 초기화하지 않는다.

## 검증 및 배포

- 기존 PR #452/PR #457의 정상 UI·Photo 저장·현장 설치 점검/승인선 유지.
- 격리 DB Auth/RLS 테스트: 운영팀장 전체 부서 명부·인사정보 교정·업무용 사진, 개별 주민번호 Vault 등록/조회, 보호 계정/일반 직원/익명 접근 거부, 급여 권한 거부, 개인정보의 명부·감사로그 유출 차단, PC/390px 브라우저 QA.
- 실제 직원정보, 주민등록번호, 급여, 계정은 테스트 목적으로 열람/변경하지 않는다.
- `taejang.co.kr`과 고정 QA가 동일 Supabase 운영 DB를 사용하므로 **업데이트 전 별도 운영 반영 승인 및 릴리스 일정을 확인한다**. 이번 PR 단계에서는 main/Production 배포를 진행하지 않는다.
