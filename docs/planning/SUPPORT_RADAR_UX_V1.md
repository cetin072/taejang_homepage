# 태장 지원사업 레이더 — MVP 화면·업무흐름 UX v1

Status: **검토 중**  
Parent: #161 / #166  
Purpose: 기존 `/app/` App Shell을 유지하면서 운영총괄과 담당자가 실제로 사용할 최소 화면·정보우선순위·상태흐름을 정의한다.

---

## 1. UX 목표

지원사업 레이더는 `공고를 많이 보여주는 화면`이 아니라 **오늘 무엇을 결정하고 무엇을 해야 하는지 보여주는 업무화면**이어야 한다.

운영총괄이 첫 화면에서 답을 얻어야 하는 질문:

1. 지금 놓치면 안 되는 공고가 있는가?
2. 이번 주 신청 여부를 결정해야 하는 사업은 무엇인가?
3. 현재 신청 중인 사업은 어디에서 막혀 있는가?
4. 누가 담당하고 있는가?
5. 최근 선정/미선정 결과와 확보금액은 얼마인가?

담당자가 첫 화면에서 답을 얻어야 하는 질문:

1. 내가 지금 확인해야 할 공고는 무엇인가?
2. 다음 행동은 무엇인가?
3. 마감까지 얼마나 남았는가?
4. 기관에 무엇을 확인해야 하는가?
5. 자료수집/신청이 어디까지 진행됐는가?

---

## 2. 메뉴 위치

기존 `/app/` 좌측 업무메뉴에 **지원사업**을 하나의 독립 모듈로 추가한다.

지원사업 하위 화면:

- 지원사업 홈
- 전체 공고
- 신청 진행
- 결과·수혜이력
- 태장 지원자격
- Source 관리 (운영총괄만)

Phase 1에서는 메뉴를 지나치게 세분화하지 않고 같은 화면 안에서 탭/필터로 흡수할 수 있다.

---

## 3. 역할별 기본 진입

### 운영총괄

`지원사업 홈`

### 담당자

`내 지원사업`

즉 같은 모듈이어도 첫 노출 우선순위는 역할에 맞춘다.

대표이사는 기존 역할별 대시보드 원칙에 따라 전체 공고보다 **핵심 추천/신청현황/선정·수혜 KPI 요약**을 우선하고, 상세는 필요 시 열람한다.

---

## 4. 운영총괄 지원사업 홈

### 4.1 상단 KPI

한 줄 또는 2행 카드:

- `신규` — 최근 확인 전 공고
- `신청추천` — recommendation이 recommend 이상
- `마감임박` — 7일 이내 행동 필요
- `신청진행` — active application
- `결과대기` — 제출 완료 후 결과 미확정

숫자 카드 클릭 시 해당 필터 목록으로 이동.

### 4.2 가장 위에 둘 영역 — 긴급확인

조건 예:

- 마감 7일 이내 + 태장 관련
- 고득점이지만 confidence low
- 자격확인이 되면 신청 가능한 조건부 공고
- 담당자 없이 진행 중
- 제출기한 임박

카드 최소정보:

- 사업명
- D-day
- 태장 적합도
- A/B/C 추천경로
- 왜 지금 봐야 하는지
- 버튼: `상세 확인`

### 4.3 이번 주 TOP 5

각 카드:

- 사업명
- 기관
- 적합도
- 신청방식
- 지원금/현물
- 자부담
- 마감
- 추천이유 1~2줄
- 확인필요사항 1~2개
- 다음 행동

점수만 큰 순서가 아니라 `실제 행동 우선순위`로 정렬한다.

### 4.4 신청 진행

표 또는 카드:

- 사업명
- 담당자
- 상태
- 다음 행동
- 마감
- 지연/위험 표시

### 4.5 최근 결과

- 선정
- 미선정
- 확보 현금
- 확보 현물가치
- 최근 결과 3~5건

## 5. 담당자 `내 지원사업`

3. 기관 확인 대기

- 운영총괄 결정

담당자는 전체 100점 평가 세부항목보다 **실행할 일**을 먼저 본다.

## 8. 공고 상세 화면

공고 상세가 이 모듈의 핵심 화면이다.

### 8.1 상단 Summary

- 사업명
- 기관
- 공고상태
- 신청기간
- D-day
- 지원금/현물
- 자부담
- 적합도
- confidence
- 최신 운영결정

### 8.2 `태장 판정` 영역

세 경로를 나란히 표시:

| 경로 | 판정 | 이유 |
| --- | --- | --- |
| A 직접 | eligible/conditional/... | 짧은 이유 |
| B 공동 | ... | ... |
| C 협력 | ... | ... |

그리고:

- `권장 참여방식`
- `태장이 할 수 있는 역할`

을 강조한다.

### 8.3 추천 이유

3~5개 핵심 bullet.

예:

- 장애인표준사업장 대상과 직접 연관
- 차량 현물지원 가능
- 창원 소재 조건 충족
- 현재 인건비·고용 우선분야와 일치

### 8.4 부족 자격 / 확인 필요

별도 경고박스:

**부족 자격**
- 중소기업확인서 현재 미보유

**확인할 것**
- 접수일 기준 확인서 필수인지
- 공동신청 허용 여부

이 둘을 혼합하지 않는다.

### 8.5 적합도 상세

운영총괄/검토자가 열어볼 수 있는 접이식 상세:

- 자격 00/30
- 전략 00/20
- 경제 00/15
- 실행 00/15
- 선정 00/10
- 시급/희소 00/10

기본 화면에서는 숫자 전체를 과도하게 노출하지 않아도 된다.

### 8.6 근거

- 원문 공고 열기
- 신청페이지 열기
- 첨부파일
- 근거 목록

AI 설명보다 공식 근거 접근을 쉽게 한다.

## 9. 운영총괄 결정 UI

공고 상세 하단 또는 고정 action area:

- `신청`
- `보류`
- `제외`

### 신청

선택 시:

1. 결정사유/메모
2. 담당자 지정
3. 첫 다음 행동
4. 내부 목표 마감일(선택)

을 한 흐름으로 처리.

### 보류

필수:

- 보류 이유
- 재검토 시점 또는 확인조건 중 하나

예:

- 중소기업확인서 취득 가능일 확인 후 재검토
- 기관 답변 후 재검토

### 제외

필수:

- 제외 이유

예:

- 신청자격 불일치
- 전략 연관 낮음
- 자부담 과다
- 일정상 준비 불가
- 중복지원 제한

과거 결정은 상세 이력에서 볼 수 있어야 한다.

## 12. 태장 지원자격 Profile 화면

### 목적

`AI가 태장을 어떤 회사로 보고 평가하는지` 운영총괄이 직접 확인한다.

### 섹션

#### 회사 기본조건
- 농업회사법인
- 주식회사
- 자회사형 장애인표준사업장
- 업종

#### 사업장
- 의창구 사업장
- 진전면 농장

#### 자격·인증
- 자회사형 장애인표준사업장 — 보유
- 중소기업확인서 — 미보유
- 기타 향후 추가

#### 사업분야
- current/developing/planned 표시

### 변경 UX

직접 기존 current row를 덮어쓰기보다는:

1. 변경내용 입력
2. 근거/확인일 입력
3. 새 Profile version 생성
4. 향후 평가에 적용

구조를 권장한다.

`기존 후보 재평가`는 Phase 1에서는 버튼/후속기능 자리만 둘 수 있고 자동 대량 AI 재평가는 후속으로 미룬다.

## 14. 수동 공고 등록 UX

Phase 1에서는 매우 중요하다.

### 최소 입력

- Source
- 공고 URL
- 사업명
- 기관
- 신청기간
- 지원규모
- 지원대상 요약
- 분야
- 원문/첨부 링크

### 반자동 도움

URL에서 안전하게 가져올 수 있는 공개 metadata가 있으면 제목/기관 등을 제안할 수 있지만 사람이 수정 가능해야 한다.

자동 파싱 실패가 공고 등록 자체를 막지 않는다.

외부 이메일/카카오 자동발송 전 앱 내부 `중요 후보`를 먼저 검증한다.

동일 공고에 같은 이유로 반복 알림이 계속 쌓이지 않도록 알림 이벤트/확인상태를 후속 데이터계약에서 검토한다.

## 17. Empty / Loading / Error

### Empty

잘못된 표현:

> 지원사업이 없습니다.

권장:

> 현재 조건에 맞는 공고가 없습니다. 필터를 지우거나 신규 Source 확인이 필요할 수 있습니다.

### Loading

전체 App Shell을 가리지 않고 지원사업 content area만 loading.

### Error

Source 수집 실패와 DB 조회 실패를 구분한다.

예:

- `기업마당 최근 수집에 오류가 있습니다. 기존 저장 공고는 계속 볼 수 있습니다.`
- `지원사업 목록을 불러오지 못했습니다.`

한 Source 장애가 전체 모듈을 빈 화면으로 만들지 않는다.

## 18. 모바일 원칙

모바일에서는 표를 그대로 축소하지 않는다.

### 목록 카드

1. D-day/우선순위
2. 사업명
3. 적합도 + 참여방식
4. 지원금/현물
5. 결정/담당자

### 상세

상단에:

- 마감
- 적합도
- 신청방식
- 다음 행동

을 먼저 둔다.

운영총괄의 `신청/보류/제외` 버튼은 오동작을 막도록 충분한 간격과 확인단계를 둔다.

## 20. 화면 정보 밀도

### 첫 화면에서 숨겨도 되는 것

- API source raw payload
- 평가 전체 evidence
- 과거 평가 버전
- 과거 결정 이력
- 긴 qualification 설명

### 첫 화면에서 반드시 보여야 하는 것

- 지금 중요한가
- 태장이 참여 가능한가
- 얼마/무엇을 지원받는가
- 언제까지인가
- 다음 행동이 무엇인가

---

## 21. 접근성

- 점수/상태를 색만으로 표현하지 않음
- 버튼 label 명확히
- 모바일 터치영역 확보
- 필터 선택상태 텍스트/aria 반영
- error는 action과 함께 제공
- D-day만 쓰지 않고 실제 마감일도 상세에 표시

---

## 22. Phase 1 화면 완료조건

- 운영총괄이 신규 고가치 공고를 3클릭 이내 상세확인 가능
- 상세에서 A/B/C, 부족자격, 확인질문, 원문을 한 흐름으로 확인
- 같은 화면에서 신청/보류/제외 결정 가능
- 신청 결정 시 담당자 지정 가능
- 담당자가 자신의 다음 행동 확인 가능
- 제출/결과/수혜이력까지 이어짐
- Source 오류가 기존 공고 조회를 막지 않음
- 모바일에서 핵심판단 정보가 표 가로스크롤 없이 보임

---

## 23. 미확정 UX

- 대표이사 전용 지원사업 KPI 카드의 정확한 위치
- 지원사업 메뉴를 상위 sidebar에 바로 둘지 `경영/사업` 그룹 아래 둘지
- 운영총괄 결정 후 대표 승인 단계를 추가할지
- 알림 읽음/확인 상태를 Phase 1에 넣을지
- 내부 comment/chat 기능을 별도로 만들지

현재는 불필요한 복잡도를 피하고 핵심 신청 workflow를 우선한다.
