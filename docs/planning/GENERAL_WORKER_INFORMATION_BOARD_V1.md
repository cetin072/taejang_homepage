# 일반 장애인 근로자용 정보게시판 기준 v1

상태: **확정**
기준 문서: 이 문서는 일반 근로자 화면의 목적·행동 범위·접근성에 관한 최우선 기준이다.

## 1. 목적

태장의 일반 근로자는 기본적으로 장애인 근로자다. 일반 근로자 화면은 사무직 업무관리 앱의 축소판이 아니라, 필요한 정보를 다시 확인해 기억과 반복 숙달을 돕는 **읽기·확인 중심 현장 정보게시판**이다.

근로자는 다음을 확인한다.

- 오늘의 업무
- 근무시간과 가까운 일정
- 중요공지
- 작업방법
- 준비물과 주의사항
- 자주 보는 안내

작업 중 지속적인 휴대전화 사용을 유도하지 않는다. 개인 휴대전화와 현장 공용 태블릿·안내화면에서 같은 웹 화면을 사용할 수 있게 설계한다.

## 2. 일반 근로자에게 요구하지 않는 입력

초기 MVP에서 일반 근로자에게 다음 행동을 기본으로 요구하지 않는다.

- 작업 시작·완료 터치
- 진행률·작업수량·실적 입력
- 출퇴근 입력
- 자유서술 업무보고
- 작업 중 상시 알림 확인
- 댓글·채팅·퀴즈·시험
- 숙련도 점수·자동평가·AI 분석

긴급상황, 몸이 힘든 상황, 업무 이해가 어려운 상황은 플랫폼 신고보다 현장관리자에게 직접 알리는 대응이 우선이다.

## 3. 현장과 플랫폼의 역할 분리

현장에는 총괄반장, 업무반장, 현장 관리자 1명이 기본적으로 함께하며 필요 시 근로자지원 담당자가 연결된다.

- 총괄반장: 공통 안내, 이동·휴식·일정과 긴급 전달
- 업무반장: 작업 순서 안내, 현장 확인, 작업방법 자료 작성·수정
- 현장 관리자: 작업반 운영, 예외 변경, 최소 기록과 인계
- 근로자지원 담당자: 적응·지원이 필요한 경우 현장과 협의

작업 배정, 시작·진행·완료 확인, 수량·실적, 문제 대응과 필요한 기록은 현장 책임자가 관리자 화면에서 처리한다. 일반 근로자 화면은 현장 대응을 대체하지 않는다.

## 4. 초기 메뉴

초기 핵심 메뉴는 다음 다섯 가지다.

1. 오늘의 업무
2. 작업방법
3. 내 일정
4. 중요공지
5. 자주 보는 안내

확인은 출근 전 또는 작업 전, 일정·근무시간 확인, 작업방법을 잠깐 다시 볼 때, 반장·관리자가 안내할 때에 한정한다. 자료를 본 뒤에는 현장 작업으로 돌아가는 흐름을 우선한다.

## 5. 첫 화면 구조

로그인 후 첫 화면에는 다음 순서로 표시한다.

1. 이름
2. 오늘 근무시간
3. 오늘의 업무
4. 작업장소
5. 담당 반장
6. 작업방법 보기
7. 오늘 꼭 확인해야 하는 중요공지 또는 가까운 일정

진행률, 실적, 통계와 다른 직원의 업무는 표시하지 않는다.

## 6. 오늘의 업무

업무카드에는 다음만 표시한다.

- 업무명
- 작업시간
- 작업장소
- 담당 반장
- 준비물
- 연결된 작업방법
- 특별 주의사항

업무가 여러 개이면 시간순으로 표시한다. 한 번에 긴 설명을 펼치지 않고 필요한 항목을 선택해 본다.

## 7. 작업방법 화면

작업방법 첫 화면에는 다음을 표시한다.

- 작업명
- 대표 사진
- 준비물
- 작업순서 보기
- 완성된 모습 보기
- 주의사항 보기

작업순서는 한 화면에 한 단계씩 표시하는 것을 기본으로 한다. 각 단계는 사진과 한 문장 한 행동 원칙을 적용하고, 마지막에는 올바른 완성 모습을 보여준다.

작업방법 목록은 복잡한 검색보다 큰 분류 버튼을 우선한다.

- 오늘 하는 작업
- 포장
- 검수
- 정리
- 안전
- 회사생활

자주 보는 자료는 근로자가 직접 복잡하게 관리하기보다 반장·관리자가 우선순위를 지정할 수 있다.

## 8. 내 일정

월간 달력보다 가까운 일정 목록을 우선한다.

- 오늘과 다음 근무시간
- 교육
- 외부활동
- 휴무
- 근무장소 변경
- 특별행사
- 차량 출발시간

근로자는 일정을 수정하지 않는다.

## 9. 중요공지

본인에게 필요한 공지만 표시한다.

- 근무시간 변경
- 작업장소 변경
- 교육
- 외부활동
- 준비물과 복장
- 안전
- 휴무
- 차량 이동

중요공지만 `확인했어요` 처리를 사용할 수 있다. 이 확인은 업무 시작·완료가 아니라 안내 확인 의미다. 모든 공지에 확인을 요구하거나 반복 알림으로 압박하지 않는다.

## 10. 자주 보는 안내

반복해서 확인하는 현장생활 안내를 제공한다.

- 출근 후 이동 장소
- 개인 물품 보관 장소
- 쉬는 시간
- 화장실 위치
- 작업복 착용
- 도구 반납
- 퇴근 전 정리
- 몸이 불편하거나 어려울 때 알릴 사람

플랫폼 신고보다 가까운 반장·관리자에게 직접 알리는 행동을 안내한다.

## 11. 근무시간 전·후와 외부활동

근무시간 전에는 오늘의 업무 제목, 근무시간과 일정을 볼 수 있다. 실행 기능은 두지 않는다.

근무 종료 후에는 오늘 업무를 계속 쌓아두기보다 다음 근무시간과 가까운 일정을 표시한다.

야외공원 청소 등 외부활동은 다음을 한 카드에 정리한다.

- 날짜
- 모이는 시간과 장소
- 준비물과 복장
- 이동방법
- 담당자
- 작업방법과 안전안내 연결

## 12. 접근성 원칙

- 큰 글자와 큰 터치영역
- 쉬운 문장, 한 문장 한 행동
- 한 화면에 적은 정보와 선택지
- 사진·그림 중심 작업안내
- 복잡한 입력·검색·선택 최소화
- 개인정보와 장애 세부정보의 불필요한 노출 금지

장애명으로 화면을 일괄 결정하지 않는다. 실제 필요한 지원방식에 따라 기본 쉬운 화면, 사진 중심, 큰 글자·고대비, 반장과 함께 사용, 관리자 대리 처리, 공용 태블릿 우선 등을 선택한다.

## 13. 개인기기와 공용기기

개인 휴대전화에서는 본인 업무와 개인 일정까지 표시할 수 있다.

공용 태블릿·안내화면에서는 작업반의 오늘 업무, 작업방법과 공통공지 중심으로 표시한다. 개인 일정, 개인 지원정보와 민감정보는 공용화면에 표시하지 않는다.

## 14. 관리자 작성 항목

### 오늘의 업무

- 업무명
- 시간
- 장소
- 담당 반장
- 준비물
- 작업방법
- 주의사항

### 일정

- 일정명
- 날짜와 시간
- 장소
- 대상
- 준비물
- 이동방법

### 공지

- 제목
- 쉬운 안내문
- 대상
- 표시기간
- 중요 여부
- 사진
- 확인 필요 여부

### 자주 보는 안내

- 안내 제목
- 쉬운 설명
- 사진
- 대상
- 표시 순서

관리자 작성 화면은 긴 문장 경고, 쉬운 문장 예시, 필수항목 누락 확인, 사진 미등록 안내와 휴대전화·태블릿 미리보기를 제공할 수 있다. AI 자동작성은 초기 필수가 아니다.

## 15. 후속 후보

청각장애인용 문장판·전체화면 큰 글자, 진동·화면 중심 알림, 저시력 확대·고대비, 화면 읽기 호환·음성 안내, 그림 중심 의사소통판은 후속 검토 대상이다. 초기 MVP 필수기능으로 확대하지 않는다.

## 16. 초기 제외

- 작업 시작·완료
- 실적과 수량 입력
- 출퇴근 체크
- 다른 직원 업무
- 전체 부서현황
- 결재
- 상담기록과 인사정보
- 업무 채팅과 자유게시판
- 전체 파일보관함
- 복잡한 검색과 통계
- 평가점수와 AI 기능

## 17. 검수 기준

- 일반 근로자가 입력 없이 오늘의 업무와 작업방법을 확인할 수 있는가
- 현장 확인과 관리자 기록의 역할이 분리되는가
- 화면이 현장 작업을 방해하거나 상시 휴대전화 사용을 유도하지 않는가
- 개인기기와 공용기기에서 같은 정보가 이해하기 쉽게 보이는가
- 공용기기에 개인정보와 지원정보가 노출되지 않는가
- 지원방식은 개인 필요에 맞추되 민감정보를 노출하지 않는가
- 접속 후 오늘 업무 확인, 필요 시 작업방법 확인, 화면 종료, 현장 복귀의 짧은 흐름이 가능한가

## 2026-10-13 확정: 직원 공지 작성 UX 1차 (Issue #444)

사용자가 Issue #444 실행을 승인했다. 직원 공지의 관리자 작성 화면만 기존 compact form과 RPC로 개선한다. 다른 작성 화면은 이번 범위에서 제외한다.

- 제목 → 본문 → 사진 → 게시 대상·시각 → 추가 설정 → 명시적 실행 버튼 → 결과 순서를 사용한다. 추가 설정의 필수 입력 오류는 자동으로 펼쳐 보여준다.
- 운영총괄/super_admin은 비공개 저장과 게시를 분리하고 대상·KST 시각·종료를 확인한 뒤 게시한다. 미래 시작은 예약으로 안내한다. 지금 게시만 현재 시각을 사용하며 지정한 예약시각을 덮어쓰지 않는다.
- 운영팀장은 초안 저장과 기존 운영총괄 상신만 사용한다. 직접 게시/예약 권한은 부여하지 않는다. 기존 게시글 편집은 게시 상태를 보존하며 취소/사용 중지는 의도적 확인 후 기존 서버 경로로 처리한다.
- 새 공지는 초안 저장 → 사진 등록 → 게시/상신 순서로 처리한다. 사진 실패 시 입력·공지 ID·완료된 사진 등록을 보존하여 재시도한다. 기존 공개글은 본문·사진 RPC의 순차 반영 및 부분 실패를 명확히 안내한다.
- 결과와 입력을 유지하고 새 공지는 별도 버튼으로 시작한다. 공개 안내는 대상·기간 조건부임을 표시한다.
- DB schema/roles/RLS/RPC/ack/push/Storage 계약과 실제 운영 데이터는 변경하지 않는다. 서버 원자성 개선은 후속 판단이며 이번 UI 변경에 포함하지 않는다.

구현 대조·320/390/1280 브라우저 및 권한 회귀 근거는 해당 Draft PR에 기록한다.

## 2026-10-13 확정: 운영팀장 일상공지 직접 게시 2차 (#446)

Issue #446의 사용자 승인 정책을 적용한다. #445 작성기를 재사용하며 공통 플랫폼 엔진으로 추상화하지 않고 태장 공지 Domain에 둔다.

- 실제 active promotion_lead + 기존 notice.manage 조건으로 전용 guarded RPC를 사용한다. 전사 대상, normal, ack=false, general/external_activity/training/transport/materials/clothing/company_life만 직접 게시·예약 가능하다.
- 그 외 분류/중요도/ack 및 근무정책·인사·급여·안전·중요 입장은 초안→운영총괄 검토·게시를 유지한다. 게시 전 대상·KST 시각·분류·중요도와 일상 안내 확인을 제공하며 텍스트 위험을 완벽히 자동 판정한다고 주장하지 않는다.
- 서버 소유 출처와 직접 발행 시각을 가산 기록한다. 기존 데이터는 NULL 그대로 두며 backfill하지 않는다. 직접 경로의 본인 공지만 수정·중지하고 타인/과거/상신·승인/운영총괄 인수 자료는 직접 관리하지 못한다. 상신 중 자료는 수정 잠금이다.
- 기존 save_notice(draft) 우회와 사진 metadata/Storage 관리도 동일 소유 경계로 제한한다. 직원 읽기·ack·outbox·잠금화면 메시지 계약은 유지한다.
- 신규 공지는 notice-admin 작성기 하나로 통일한다. 구 information_publication_requests의 기존 pending/changes_requested/처리 이력과 보완 재상신은 그대로 유지한다.
- 새 글 draft→사진 등록 확인→최종 게시/상신, 응답 불명 시 파일/입력/ID 보존 원칙을 유지한다. 물리 삭제나 운영 데이터·계정 변경 없이 격리 DB에서 검증한다.

## 2026-10-14 확정: 직원앱 공지 발견과 읽음 표시 (#449)

사용자 지시에 따라 기존 큰 공지 카드·목록·상세와 조회/ack RPC를 재사용한다.

- 홈은 최신 미확인 공지 제목(최대 2줄), KST 게시 시작일, 미확인 개수를 표시하고 해당 상세로 이동한다. 지난 공지 목록은 별도 버튼으로 항상 접근한다.
- 게시 후 3일은 새 공지 강조, 이후에도 미확인은 작은 표시로 유지한다. 서버가 종료/비공개/대상 제외한 공지는 현재 목록에서 제거한다.
- 일반 공지는 정상 상세 텍스트가 렌더링된 뒤 기존 chunk-safe SecureStore에 사용자 ID별 공지 ID/버전만 저장한다. 필수 확인은 열람으로 완료하지 않고 기존 acknowledge_notice 버튼/버전 계약을 따른다.
- 홈/목록은 focus(최초/상세 복귀 포함), foreground 시 기존 목록 RPC 1회 및 캐시를 재사용한다. 숨은 화면 조회·폴링·팝업 없음. 실패는 공지 없음과 구분하고 재시도를 제공한다. 계정 전환/화면 이탈 이전 지연 응답을 버린다.
- 현재 서버 RPC 상한 200건을 사용한다. 이 한계 도달 시 개수는 하한(이상)으로 표시하며 200건을 넘는 목록의 정확한 집계/페이지 조회는 서버 계약 후속이다. 현재 공유 서버 노출 공지는 1건이다.
- 일반 읽음은 기기 내 상태이며 재설치/저장소 삭제/다른 기기에서는 다시 표시될 수 있다. 기기 간 일반 읽음 동기화는 실제 필요 확인 및 별도 승인 후 서버 변경으로 다룬다. 필수 확인은 기존 서버 저장을 따른다.
- 이번에는 DB/Auth/RLS/RPC 의미·실제 공지·직원·출퇴근·푸시·Play·강제 업데이트를 변경하지 않는다. QA 앱의 실제 공지 조회와 모의 근태 쓰기 금지 경계는 유지한다.
