## 3. 이번 개발 범위

### A. 거래처 관리

하나의 기준정보 체계에서 다음을 관리한다.

- 거래처명, 개인/기업 구분
- 사업자등록번호(기업인 경우)
- 연락처 및 거래 담당자
- 고객·공급처·영업 관계 구분
- 거래 상태(활성/중단)
- 담당 영업자
- 거래 관련 메모

하나의 회사가 고객이면서 공급처일 수도 있으므로 불필요한 중복 등록을 방지한다.

개인 고객은 필요한 최소 정보만 수집한다. 개인정보 접근은 서버 권한으로 제한한다.

### B. 영업자 관리

태장의 영업자는 거래처를 확보한 뒤 해당 거래처를 계속 관리하는 구조다.

- 영업자 기본정보
- 확보·담당 거래처 연결
- 담당 관계의 시작일·변경 이력
- 거래별 영업비 조건
- 영업자별 매출 조회를 위한 연결 관계

**영업비는 전체 거래에 공통 비율을 적용하지 않는다.**

각 거래마다 고정 금액 또는 비율 등 실제 조건을 기록할 수 있도록 한다. 영업비 지급·원천징수 계산·지급 승인은 이번 개발에서 실행하지 않는다.

### C. 품목·서비스 관리

상품과 용역을 하나의 품목 기준정보에서 관리한다.

구분:

- 상품: 소금, 향후 장류 등
- 용역: 환경정비 등
- 원재료·포장재: 향후 재고관리 대상

기본 필드:

- 품목코드 및 이름
- 유형
- 단위
- 기준 단가(선택)
- 부가세 관련 구분
- 재고관리 여부
- 사용 상태

거래 당시의 실제 단가는 거래 기록에 별도로 보존한다. 기준 단가가 변경되어도 과거 매출 금액이 바뀌면 안 된다.

재고관리 여부는 준비하되, 입출고·재고 계산은 후속 단계에서 개발한다.

### D. 용역 계약·매출 관리

현재 실제 운영 방식:

- 거래처별 1년 계약
- 월 고정 금액은 거래처마다 다름
- 청구 시점도 거래처마다 다름
- 매월 공문·견적서·거래명세서·작업결과보고서 사용
- 갱신 계약은 대면 진행

구현:

- 거래처와 계약 연결
- 계약 시작일·종료일
- 월 계약 금액 및 세금 구분
- 거래처별 청구 기준
- 계약 상태
- 해당 월 매출 등록
- 같은 계약·월의 중복 매출 방지

계약을 등록하면 월 매출을 간단하게 생성·확인할 수 있는 흐름을 우선한다.

정기 매출 자동 생성 배치나 계약 갱신 자동화는 도입하지 않는다.

기존 **거래처 문서 관리**에 등록된 정보와 연결 가능한 구조를 우선 검토한다. 기존 문서·확정 데이터·계산 결과를 변경하거나 이중으로 생성하지 않는다.

### E. 소금 주문·판매 관리

현재 소금 판매 방식:

- 기업·개인 모두 판매
- 쇼핑몰·전화·카카오톡·기업 발주서로 주문
- 공급처 한 곳에서 고객에게 직접 배송
- 거래별 판매 금액 및 영업비 상이

구현:

- 주문 거래처·고객
- 주문 유입 경로
- 판매 품목
- 수량·실제 판매 단가·총액
- 관련 공급처
- 담당 영업자
- 배송 방식: 공급처 직배송
- 배송 상태
- 주문일·매출 기준일
- 작성·확정 상태

직배송 주문은 태장 창고 재고를 자동 차감하지 않는다.

확정 전 거래는 수정할 수 있지만, 확정된 거래의 원본 금액과 핵심 정보는 임의 덮어쓰기하지 않는다.

후속 취소·반품·정산 조정을 연결할 수 있도록 거래 고유 ID와 이력 구조를 보존한다.

### F. 매출 목록 및 상세

매출 관리 화면에서는 최소한 다음을 제공한다.

- 기간별 매출 목록
- 거래처별 조회
- 용역/상품 구분
- 담당 영업자
- 작성·확정 상태
- 매출 금액
- 거래 상세 및 연결된 계약·주문 확인

초기에는 복잡한 BI 대시보드를 만들지 않는다.

기존 ERP 대시보드와 권한 체계를 유지하면서 실제 작동하는 메뉴만 추가한다.

## 4. 기존에 확정된 후속 정책

아래 정책은 데이터 구조 확장 시 반드시 보존한다. 다만 이번 V1에서 전체 정산 기능을 구현할 필요는 없다.

**수금·영업비**

- 거래별로 전액 입금 후 지급 또는 부분 입금 비율 정산 선택
- 영업비는 거래별 조건이 다름
- 고객 입금·발행 증빙 확인 후 운영총괄 승인
- 지급 완료 후 취소·반품 시 상계·별도 반환·조정·면제 중 선택
- 기존 지급 기록 삭제 금지

**거래 변경**

- 확정 전에는 직접 수정 가능
- 확정 후 변경은 원본을 보존하고 조정 기록으로 관리
- 부분 환불과 부분 입금 허용
- 마감 후 기본 잠금
- 예외적으로 운영총괄이 사유를 기록하고 마감 해제 가능

**승인**

- 정산 최종 승인권자는 운영총괄
- 대표이사 추가 승인 단계는 기본적으로 없음
- 단, 회사 직책과 개인 전용 계정 권한은 구분

**전자세금계산서**

- 현재 홈택스에서 직접 발행
- 1차는 발행 결과 수기 등록
- 후속으로 홈택스 발행 내역 파일 대조
- 발급 API, 자동 로그인, 세무 신고 자동화 제외
- 3.3% 공제의 세무 적용은 검토 전 자동 계산·확정 금지

**구매·재고**

- 일상 물품 구매는 바로 비용 등록 가능해야 함
- 필요한 품목만 재고관리
- 소금은 공급처 직배송
- 장 사업 제조 방식 미확정
- 생산 BOM·제조 LOT·발효·숙성·기한 관리 보류

## 5. 데이터 설계 원칙

이번 단계의 데이터 모델은 아래 관계를 수용해야 한다.

```text
거래처
 ├── 고객
 ├── 공급처
 └── 담당 영업자
          │
          ▼
     계약 / 판매 주문
          │
          ▼
       매출 거래
          │
          ├── 거래별 품목·금액
          ├── 거래별 영업비 조건
          ├── 향후 수금 기록
          ├── 향후 공급처 지급
          ├── 향후 세금계산서
          └── 향후 반품·환불·조정
```

구현 원칙:

1. 정규화는 필요한 수준으로만 적용한다.
2. 동일 정보의 소유자와 원본을 명확히 한다.
3. 거래별 금액·조건은 기록 당시 값을 보존한다.
4. 확정 거래는 무단 수정·삭제를 방지한다.
5. 고객·영업자·거래 관계는 서버에서 검증한다.
6. RLS와 서버 권한 검사를 적용한다.
7. 미래 기능을 위해 빈 테이블을 대량 생성하지 않는다.
8. 기존 Auth·직원·근태·연차·급여·홍보 데이터는 변경하지 않는다.

Supabase 스키마 변경이 필요하면 migration 파일을 작성하고 격리된 테스트 환경에서 검증한다.

운영 DB에는 사용자 별도 승인 없이 적용하지 않는다.

## 6. 화면 설계

기존 태장 ERP의 사이드바·디자인·화면 전환 방식을 재사용한다.

필요한 기능은 다음 네 영역으로 구성하되, 불필요한 메뉴 분할은 하지 않는다.

1. 거래처·영업자 관리
2. 품목·서비스 관리
3. 용역 계약 관리
4. 매출·판매 관리

현재 없는 기능을 마치 작동하는 것처럼 빈 메뉴로 노출하지 않는다.

PC 중심으로 설계하고, 작은 화면에서도 목록·입력·조회가 무너지지 않도록 한다.

단순한 등록·수정에 여러 단계의 마법사나 불필요한 승인 화면을 만들지 않는다.

## 7. 권한·보안

기존 역할·Capability 구조를 우선 사용한다.

첫 실행본은 운영총괄을 기준으로 설계한다.

- 조회, 작성·수정, 확정 권한을 서버에서 구분
- 역할 시뮬레이션으로 상위 권한 우회 금지
- 다른 직원에게 임의로 금전 정보 접근권 부여 금지
- 확인되지 않은 사용자에게 민감 거래 정보 노출 금지
- 실제 결제·송금·세금계산서 발행 기능 구현 금지
- 변경 이력·최종 수정자 기록

권한 구조에 중요한 변경이 필요한 경우 실제 DB 적용 전에 근거를 정리한다.

## 8. 구현 순서

**Step 1 — 기존 구현 확인**

현재 코드·DB·PR과 기능 겹침 확인, 재사용 대상 선정.

**Step 2 — 최소 데이터 모델**

거래처·영업자·품목·계약·매출에 필요한 스키마 및 migration 작성.

**Step 3 — 실제 입력·저장·조회**

거래처 등록 → 품목 등록 → 용역 계약 또는 소금 판매 등록 → 매출 확인까지 작동시키기.

**Step 4 — 화면 연결**

기존 ERP 메뉴·대시보드·권한 구조에 연결.

**Step 5 — 검증**

입력·수정·확정·조회·중복 방지·권한·오류 처리 테스트.

**Step 6 — Draft PR 및 QA**

실행 결과를 GitHub에 기록하고 Preview에서 검수 가능한 범위까지 진행.

코드만 작성하고 실행되지 않는 상태를 완료로 보고하지 않는다.

## 9. 필수 테스트

다음 사례를 검증한다.

- 기존 등록 거래처와 중복 등록 처리
- 한 거래처에 여러 영업 관계 연결
- 거래처 담당 영업자 변경 후 과거 거래의 담당자 보존
- 거래별 서로 다른 품목 가격·영업비 조건
- 용역 계약 월별 매출 중복 방지
- 기업 소금 주문 및 개인 소금 주문
- 공급처 직배송 시 태장 재고 미변경
- 기준 단가 변경 후 과거 거래 금액 불변
- 확정 거래의 무단 수정·삭제 차단
- 미인증·권한 없는 사용자 조회·변경 차단
- 기존 출근부·연차·급여·홍보 기능 회귀

변경 범위에 맞게 기존 `package.json`의 검사 명령을 사용하고, 최소한 관련 플랫폼 회귀와 Netlify 빌드 검증을 수행한다.

로컬 또는 격리된 DB에서 실제 데이터 저장·조회 흐름을 확인하고, 단순 정적 코드 검사만으로 기능 완료를 선언하지 않는다.

## 10. 이번 작업의 제외 범위

- 수금·영업비 실제 지급 처리
- 공급처 지급 및 자동 송금
- 홈택스 API 연동
- 세금계산서 자동 발행
- 재고 수불·제조·생산관리 전체
- 장 사업 생산 기능
- ERP 전체 메뉴 빈 화면 생성
- 출근앱·업무수첩 통합 구조 변경
- 기존 업무수첩 데이터 이전
- 운영 DB의 기존 데이터 삭제·초기화
- 관련 없는 코드 전면 리팩터링

## 11. 완료 기준

다음 시나리오를 실제 실행할 수 있어야 한다.

**시나리오 A — 용역 매출**

거래처 등록 → 1년 계약 등록 → 해당 월 매출 생성 → 거래처별 매출 목록·상세 조회.

**시나리오 B — 소금 판매**

고객 등록 → 상품 선택 → 판매금액과 영업자 조건 등록 → 공급처 직배송 상태 기록 → 매출 조회.

두 시나리오 모두 실제 저장·재조회되고 권한 검증이 정상 작동해야 한다.

## 실행 결정 (2026-11-05)
- 사용자 확정 지시를 개발 기준으로 보존한다. 태장 Domain이며 기존 Auth/Capability/감사로그/UI를 재사용한다.

- 단일 회사 V1, organization_key로 회사 경계를 표시한다. 상품 주문과 매출은 V1에서 한 UUID 원본이 소유하며 품목 행과 불변 확정 snapshot, 변경 이력을 둔다.
- KRW 공급단가×수량의 공급가(원 단위 반올림)와 직접 입력한 실제 부가세를 기록한다. 세무 판정·영업비 지급·원천징수 계산은 하지 않는다. 면세/영세율의 부가세는 0이다.
- 신규 read/write/confirm Capability를 구분하며 실제 운영총괄·역할 체험 아님을 서버에서 확인한다. 개인 위임은 비활성이다. 운영 권한은 적용하지 않는다.
- 기존 isolated PostgreSQL 테스트 패턴과 실제 Auth/Data API CI를 사용한다.
- 구현 대조: A~F 구현 완료(격리 DB·브라우저 검증 완료, 전체 Auth CI 확인 중). 수금·지급·자동발행·재고·조정 실행은 의도적 제외. Production migration/main/정식 배포 미승인.
