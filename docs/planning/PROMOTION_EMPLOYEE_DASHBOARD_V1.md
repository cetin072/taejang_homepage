# 홍보직원 대시보드 v1 확정 기획

- 상태: `확정`
- 현재 개발 대상: 태장 업무 플랫폼의 첫 운영 모듈인 홍보 모듈
- 원칙: 홍보직원은 작성과 자료 입력에 집중하고, 중요도·공개 위험·승인선 판단은 시스템과 관리자가 담당합니다.

## 1. 홍보직원의 하루

출근 후 태장 업무 플랫폼에 본인 계정으로 로그인합니다.

1. 오늘의 홍보 업무 확인
2. 직접 촬영 또는 다른 팀이 카카오톡으로 전달한 자료 확인
3. 사진 선별과 자료 정리
4. 홈페이지 자체 글 작성 또는 외부 SNS 게시
5. 외부 SNS 콘텐츠를 홈페이지 링크 카드로 등록
6. 임시저장과 미리보기
7. 승인 요청
8. 승인 대기 또는 `보완 필요` 처리
9. 게시 완료 확인
10. 퇴근 전 오늘의 완료 현황 확인

플랫폼 기록이 일일 업무 결과가 되며 별도의 중복 업무일지 작성을 요구하지 않습니다.

## 2. 대시보드 배치 순서

1. 인사말과 날짜
2. 오늘 해야 할 일
3. `보완 필요`와 오늘 마감
4. 빠른 작업
5. 촬영·게시 일정
6. 승인 현황
7. 최근 작업
8. 오늘 완료 현황
9. 이번 달 기록과 대표 사진

행동이 필요한 항목을 성과 통계보다 위에 배치합니다.

## 3. 오늘 해야 할 일 생성 방식

초기 버전에서는 다음 세 가지를 지원합니다.

- 정기 업무 자동 생성
- 홍보팀장 업무 배정
- 홍보직원 직접 추가

행사 일정에서 업무를 자동 생성하는 기능은 후속 단계로 보류합니다.

## 4. 빠른 작업

- 홈페이지 글쓰기
- 외부 콘텐츠 등록
- 내 콘텐츠 관리
- 사진·자료 정리

원본 사진 전체를 플랫폼에 저장하지 않습니다.

- 원본 사진: 별도 공유 드라이브 또는 내부 공유 폴더
- 플랫폼: 대표 이미지와 게시용 선별 사진

## 5. 직원 화면 상태 용어

- `작성 중`: 아직 작성하거나 정리하는 상태
- `승인 대기`: 관리자가 확인 중이며 직원의 즉시 행동이 필요하지 않은 상태
- `보완 필요`: 관리자가 의견과 함께 되돌려 직원이 다시 수정해야 하는 상태
- `게시 예정`: 승인 완료 후 게시 시점 대기
- `게시 완료`: 공개 완료
- `숨김`: 공개를 일시 중지
- `보관`: 운영 목록에서는 제외하고 기록 유지

직원이 `승인 요청` 버튼을 누른 이후 화면 상태는 `승인 대기`로 표시합니다.

## 6. 승인 흐름

### 일반 콘텐츠

홍보직원 작성 → 홍보팀장 확인 → 게시

### 중요 콘텐츠

홍보직원 작성 → 홍보팀장 확인 → 운영총괄 최종 승인 → 게시

### 대표이사 확인 콘텐츠

홍보직원 작성 → 홍보팀장 확인 → 운영총괄 확인 → 대표이사 확인 → 게시

대표이사 확인은 대표이사 명의 글, 중대한 공식 입장, 주요 모회사 발표, 중요한 협약·계약·경영수치, 사고·분쟁·언론 대응 등에 제한합니다.

## 7. 홍보직원의 판단 범위 최소화

홍보직원에게 아래 판단을 맡기지 않습니다.

- 일반 콘텐츠와 중요 콘텐츠 구분
- 운영총괄 또는 대표이사 승인 필요 여부
- 법률적으로 위험한 표현인지 여부
- 모회사 관련 정보의 공개 가능 여부
- 민감한 개인정보나 공식 경영수치의 공개 적절성

직원은 사실과 자료를 입력하며 판단이 어려울 때 `잘 모르겠음`을 선택할 수 있습니다. `잘 모르겠음`은 오류가 아니라 관리자 확인이 필요한 정상 상태입니다.

## 8. 직원 작성 화면의 간단한 확인 항목

- 글 종류
- 작성 명의
- 관련 기관
- 사람이 나온 사진: 있음 / 없음 / 잘 모르겠음
- 숫자·금액 포함: 있음 / 없음 / 잘 모르겠음
- 게시 희망일

직원에게 긴 위험 체크리스트나 중요도 선택 화면을 제공하지 않습니다.

## 9. 시스템의 승인선 자동 제안

시스템은 콘텐츠 유형과 입력값으로 승인선을 제안합니다.

- 보도자료 → 운영총괄 승인 추가
- 대표이사 명의 → 대표이사 확인 추가
- 모회사 관련 새로운 정보 → 운영총괄 승인 추가
- 인물 사진 있음 또는 잘 모르겠음 → 팀장 공개 확인 표시
- 숫자·금액 있음 또는 잘 모르겠음 → 운영총괄 확인 표시
- 일반 행사 후기·승인된 반복 형식 → 팀장 승인

AI가 단독으로 승인선을 확정하지 않습니다. 규칙 기반 제안 후 홍보팀장이 최종 확인합니다.

## 10. 홍보팀장의 역할

- 사실관계와 표현 확인
- 사진과 공개 가능 여부 확인
- 일반 콘텐츠 승인·게시
- `보완 요청`과 구체적인 수정 의견 작성
- 중요 콘텐츠를 운영총괄에게 전달
- 시스템 분류가 불충분한 경우 승인선 상향

위험 조건이 있는 콘텐츠를 임의로 일반 콘텐츠로 낮추지 못하도록 시스템 제한을 둡니다.

## 11. 직원 대시보드 핵심 카드

### 행동 필요

- 보완 필요
- 오늘 마감
- 임시저장

### 승인 현황

- 승인 대기
- 게시 예정
- 게시 완료

### 최근 작업

콘텐츠 제목, 콘텐츠 종류, 현재 상태, 최근 수정 시각을 표시하고 바로 열기·수정이 가능해야 합니다.

### 기록과 성취

오늘, 이번 주, 이번 달, 올해, 누적 콘텐츠 수와 최근 대표 사진을 화면 하단에 표시합니다. 평가나 직원 간 순위가 아니라 기록의 성취감을 제공하는 용도입니다.

## 12. 초기 버전에서 제외

- SNS 자동 게시
- 카카오톡 자동 수집
- 조회수·좋아요·전환율 등 고급 성과 분석
- 개인 점수·직원 순위
- 원본 사진 전체 보관
- 대표이사·운영총괄의 회사 전체 기능을 직원 화면에 혼합
- 행사 일정 기반 업무 자동 생성

## 13. 개발 검수 기준

- 직원은 중요도를 직접 선택하지 않아도 승인 요청을 완료할 수 있어야 합니다.
- `잘 모르겠음`을 선택하면 관리자 확인 흐름으로 안전하게 연결되어야 합니다.
- `보완 필요`가 `승인 대기`보다 높은 우선순위로 표시되어야 합니다.
- 일반 콘텐츠와 중요 콘텐츠의 승인선이 규칙에 따라 달라져야 합니다.
- 직원은 자신이 작성하거나 배정받은 업무만 기본적으로 확인해야 합니다.
- 대시보드는 평가보다 누락 방지와 업무 수행을 지원해야 합니다.
- 공개 홈페이지와 내부 업무 데이터의 권한·보안 경계를 분리해야 합니다.

## 2026-10-07 운영총괄 본인 작성 경로 (사용자 확정)

적용: PR #401, 태장 Domain의 기존 홍보 workflow 보정. 새 공통 플랫폼·상태·테이블은 만들지 않는다.

- 운영총괄 직접 작성은 임시저장 / 운영팀장 선택 검토 / 바로 공개 / 실제 예약일 선택을 지원한다.
- 운영팀장 사전 검토는 선택이다. 보완 요청은 운영총괄로 돌아가고 검토 완료 후 운영총괄 자기승인 단계를 만들지 않는다.
- 대표이사 명의 및 기존 required/minimum stage=ceo는 CEO Gate를 유지한다. 선택 검토 없이 대표이사 요청 또는 운영팀장 검토 완료 후 대표이사 요청으로 이어진다. 승인 후 운영총괄 공개·예약이 가능하다.
- 서버에서 active operations_manager, 기존 edit_any_unpublished 권한, content owner와 현재 revision author가 auth.uid()인지 검사한다. 직접 작성 lane은 제출 전 revision에 기록하고 잠근다. 다른 작성자·이미 공개된 글에 적용하지 않는다.
- 전역 promotion.queue_publication과 기존 홍보직원/운영팀장 승인선을 변경하지 않는다. 허위 승인 행을 만들지 않는다. 실제 행동은 audit에 기록한다.
- 운영총괄이 실제 최종 승인자인 operations 단계에서 승인하면 별도 발행 단계를 요구하지 않고 즉시 홈페이지에 공개한다. CEO Gate 대상은 운영총괄 승인 후에도 즉시 공개하지 않고 대표이사 확인으로 진행한다.
- 임시저장한 글은 작성 화면에 남고, 보낸 글은 기존 원작성자 필터를 유지한다. 보류·재개와 역할 체험 보호도 유지한다.
- 희망일과 실제 예약일은 구분한다. 기존 실제 콘텐츠는 migration으로 승인·공개·변경하지 않는다.

## 2026-10-08 운영총괄 공개글 문구 정정 (사용자 확정, Issue #414)

- 태장 Domain의 기존 공개 홍보글 관리·편집 UI와 revision/audit를 재사용한다.
- active operations_manager + promotion.review_public_change capability만 실행하며, 본인 원작성 또는 본인의 최신 최종 operations 승인 기록이 있는 published/hidden 글만 수정한다. 24시간 제한은 없다.
- 제목·요약·본문만 새 locked revision으로 기록한다. 작성 명의·종류·승인선·미디어·첨부·링크·ID·URL·최초 게시일·공개/숨김 상태는 유지한다.
- 서버 minimum/policy CEO 대상과 CEO 검토 이력이 있는 글은 즉시 텍스트 수정에서 제외하고 기존 승인 절차를 유지한다. 텍스트 RPC로 위험 분류·명의를 낮출 수 없다.
- 수정자·시각·사유·이전/새 revision ID는 감사로그에 남긴다. 원문과 승인 이력은 덮어쓰거나 위조하지 않는다. prepublication fully-approved/queue 계약은 변경하지 않고 공개 feed/detail은 현재 revision을 읽는다.
- 열었을 때 revision ID로 저장 시 충돌을 차단한다. 실패 시 입력을 보존한다. 사유 기본값은 '게시 후 문구 정정'이다.
- 운영팀장의 24시간 직접 수정/이후 수정 요청과 직원 권한은 그대로 유지한다. 정적·외부 원본 편집은 제외한다.
- 실제 게시글은 읽기 전용으로 대조한다. 3건 추적 요청은 사용자가 현재 첫글 1건이면 충분하다고 정정하여 1건 기준으로 확인한다. 합성 mutation 테스트는 격리 DB만 사용한다.


## 2026-10-16 홍보 작성 화면 정리 (사용자 확정)

- 태장 Domain의 기존 buildComposer/previewCard/savePromotion을 재사용한다. 제목→본문→사진→게시글 미리보기→컴팩트 선택 설정→외부 링크 묶음→기존 저장/승인 버튼 순서를 사용한다.
- 작성 중 미리보기는 현재 브라우저 입력으로만 렌더링하며 저장 RPC를 호출하지 않는다. 제목/본문은 안전한 textContent, 줄바꿈 유지, 대표/첨부 사진·연결 링크를 반영한다. 기존 저장글 미리보기와 현재 입력 미리보기는 서로 제거하지 않는다.
- 새 홍보직원 원고는 기존 태장 소식 종류를 유지하고 종류/승인 판단을 강요하지 않는다. 운영팀장·운영총괄의 기존 종류/명의/실제 예약/CEO gate와 승인 RPC·DB 계약은 변경하지 않는다.
- 게시 희망일·중요 금액 판단 등 선택 설정은 기존 CSS로 PC 2~3열, 모바일에서 읽기 좋은 폭을 유지한다. 1440/768/390/320px에서 검사한다.
- 링크 종류 판단·메타데이터 가져오기와 직접 입력 보호를 유지한다. 사진 순서/제거 시 첫 첨부 대표 이미지 및 미리보기를 갱신하고 부분 업로드 결과·저장 실패 입력·재시도 ID를 보존한다.
- 새 프레임워크/작성기/MutationObserver를 추가하지 않는다. 운영 데이터·공개글·Hosted migration·main 병합·Production 배포는 별도 승인 전 수행하지 않는다.

## 2026-10-16 홍보 작성 UI 전 역할 확대 (사용자 승인)

- **운영총괄(`operations_manager`)을 공통 작성 UI의 원본 기준**으로 정하고 운영팀장(`promotion_lead`)·홍보직원(`promotion_staff`)은 기존 하나의 `buildComposer`에서 직책별 사용 권한에 맞게 항목을 줄여 사용한다. 모든 역할은 제목 → 본문 → 사진 추가·순서·삭제 → 작성 중 미리보기 → 컴팩트 설정 → 외부 링크 → 저장·상신/게시 버튼을 공유한다. 역할별 편집기를 복제하지 않는다.
- 운영팀장에게는 글 종류·운영총괄 검토 요청을, 운영총괄에게는 글 종류·작성 명의·실제 예약일·직접 공개·대표이사 승인 경계를 기존 그대로 제공한다. 운영총괄의 실제 예약일은 공통 선택 설정 뒤(외부 링크 앞)에 모으고, 대표이사 확인 대상에서는 숨긴다.
- 모든 공통 업무 UI의 기준은 운영총괄 화면이고, 다른 직책은 같은 기준 UI에서 가능한 기능만 사용한다. 다만 장애인 직원용 간결한 사용화면, 대표이사용 압축 대시보드처럼 목적과 접근성 기준이 다른 화면은 업무에 맞게 유지한다. 이는 기존 전체 플랫폼 화면을 한꺼번에 전면 재작성하라는 뜻이 아니다.
- UI 통일은 권한 통일이 아니다. `save_promotion_draft` / `save_operations_promotion_draft`, `submit_promotion_revision` / `submit_operations_promotion_revision`, `queue_operations_owned_promotion` 및 대표이사 승인·실제 게시 기준은 수정하지 않는다. 홍보직원에게 관리자 명의·직접 게시·예약 게시 권한을 부여하지 않는다.
- 기존 320/390/768/1440px 격리 합성 Playwright 검사를 세 역할로 확대해 동일한 필드 순서, 실시간 미리보기, 역할별 선택·버튼, 대표이사 승인 가드, 모바일 가로 넘침을 검수한다. 실제 홍보글·DB·Production 배포는 별도 사용자 승인 전 건드리지 않는다.

## 2026-10-27 공식 블로그 링크 대표사진 자동 첨부 (사용자 확정)

- 공식 `taejang-official` 블로그의 게시물 URL 입력 후 기존 인증·capability quota 메타데이터 API에서 원문 대표사진을 확인한다. 다른 블로그·언론사는 기존 참고 이미지 정책을 유지한다.
- 기존 공식 썸네일 검증·다운로더를 재사용한다. `blogthumb.pstatic.net` HTTPS만 허용하며 공개 IP, credential/port, redirect 거부, 12초 제한, 스트림 1,500,000바이트 제한, JPEG/PNG/WebP 시그니처·MIME을 검증한다. 이미지 URL은 클라이언트 입력으로 받지 않는다.
- 브라우저에서 검증 바이트를 decode 후 기존 `uploadImage`로 로그인 사용자의 Storage 경로에 저장한다. 기존 `public_media` JSON의 공개 URL과 `official_blog_post` 번호로 저장·재진입 중복을 방지한다. Migration·권한 변경은 없다.
- 기존 제목·본문·수동 첨부를 덮어쓰지 않는다. 제목·본문은 비었을 때만 채우며 새 사진은 뒤에 추가한다. 기존 사진 편집의 앞으로/뒤로·사진 빼기로 대표사진 변경·제거가 가능하다. 제거한 사진은 명시적 재시도 전 자동 재추가하지 않는다.
- URL 변경·화면 이탈 후 늦은 결과는 첨부하지 않는다. 업로드 도중 이동하면 미첨부 Storage 객체가 남을 수 있으며 자동 삭제하지 않는다.
- 실패 시 이유·재시도/수동 첨부를 안내하고 기존 입력·첨부를 보존한다. 공개 화면은 PR531의 승인 첨부→공식 기본 이미지 정책을 그대로 사용한다. 승인선·저장/발행 RPC는 변경하지 않는다.
- 이미 발행된 글은 자동 수정하지 않는다. 기존 권한 있는 수정본·승인 절차에서 사진을 확인하여 반영한다. 운영 DB 직접 갱신과 실제 시험 발행은 제외한다.

## 2026-10-28 기존 공개 홍보글 누락 사진 보완 (Issue #542, 구현 초안)

- 문제: 기존 공개글 8건 중 3건은 링크의 원본 `hero_image_url`만 있고 승인된 `public_media`는 빈 배열이다. 공개 사이트의 회사 기본 사진은 폴백이며 콘텐츠 복구 완료가 아니다.
- **제한된 수정:** `published` 공개글 중 실제 공개 첨부가 0장인 경우에만 새로운 승인 사진 **1장 추가**를 제안한다. 이미 사진이 있는 글의 교체·삭제나 문구 정정은 이 경로에서 지원하지 않는다. 대표이사 승인 이력/필요 글은 제외한다.
- 기존 작성자·원래 게시일·URL·제목·본문·외부 링크·승인 기록·공개 상태를 그대로 보존한다. 수정 전 원본 revision은 불변이고, 운영총괄의 보완 사유와 실제 사진의 공개 출처 확인 후 새로운 잠금 revision을 생성해 감사를 남긴다. 변경 중 충돌은 거부한다.
- 작업자는 사진의 관련성과 사용권, 인물 촬영 동의를 직접 확인한 뒤 확정해야 한다. 외부 기사 이미지는 원문 URL만으로 무단 복사하지 않는다. 태장 공식 블로그 사진은 기존 PR #539의 보안 검증·Storage 업로드를 재사용한다. 실제 접근이 막히면 수동 사진 파일을 받는다.
- 회사 승인 자산인 개소식 사진은 해당 개소식 콘텐츠에서만 제안한다. 그 외에는 인증된 운영총괄 계정이 공개 `promotion-media`에 직접 업로드한 자사 사진만 허용한다. 미확인 URL 입력이나 외부 핫링크를 붙이는 기능은 만들지 않는다.
- 승인 필요 경계: 새 정정 RPC는 역할과 감사 경계가 중요하므로 **Draft PR 및 격리 DB 검증 뒤, 운영 migration·사용자 실제 글 반영·병합은 별도 명시 승인을 받아야 한다**. 마이그레이션을 배포하지 않은 브라우저 Preview는 실제 저장 검수 PASS로 취급하지 않는다.
- 기존 다른 게시물의 사진/데이터는 무단 수정하지 않고, 72시간 정규 배포 정책을 유지한다.
