# 출퇴근 → 운영팀장 확인 → 일일 확정 1차 계약

상태: 사용자 승인 확정 (2026-09-19)
상위 Goal: #226 / 구현: #247

## 목표와 범위
일반직원이 기존 Android 앱에서 출퇴근을 찍고 공지/공식채널을 확인한다. 운영팀장이 앱 기록과 수기 출근부를 대조하여 누락을 입력하고 기존 시각을 정정한다. 일일 확정 revision을 누적하고 별도 급여 프로그램이 확정본만 조회한다.
이미 구현된 Auth/Employee/출퇴근/공지/공식채널을 재사용한다. 홍보 및 다른 모듈 확장은 하지 않는다.

## 사용자 결정
- 운영팀장(promotion_lead)은 근태 누락 입력과 기존 시간 정정을 직접 수행한다.
- 최초로 비어 있는 시간을 채울 때 사용자가 사유를 쓰지 않는다. 시스템은 수기 입력 유형, 작성자, 작성시각을 남긴다.
- 기존 GPS 또는 수기 시간을 바꾸거나 무효 처리할 때 사유를 입력한다.
- 무효화 이력 또는 이전 수기 시간이 있으면 화면이 비어 있어도 최초 누락이 아니다.
- GPS 원본과 이전 보정·확정본을 덮어쓰거나 삭제하지 않는다.
- payroll.manage, employee.update 등 무관한 권한은 확대하지 않는다.

## 저장 안전규칙
UI의 빈칸 여부를 신뢰하지 않는다. 서버가 유효 기록과 보정 이력을 잠금 상태에서 확인한다. 화면을 연 뒤 기록이 바뀌면 STALE_ATTENDANCE로 저장을 중단하고 새로 불러오게 한다. 출근/퇴근 순서, 재직기간, 미래시각 가드는 기존 규칙을 유지한다.
원본 GPS가 없는 수기 기록에는 가짜 좌표/정확도를 넣지 않는다. 최초 누락 입력의 자동 설명은 사용자 사유 입력을 대신하는 시스템 메타데이터다.
운영팀장 자신의 근태는 본인이 보정하지 않고 운영총괄이 검토한다. 이는 기존 자기 예외승인 금지와 같은 안전선이다.

## 단계별 작업과 완료 기준
### A. 수기입력/보정 경로
- [ ] attendance.correct를 운영팀장에게 한정 부여; 기존 capability/simulation 가드 유지
- [ ] 최초 누락 무사유 입력, 기존/과거 기록 변경 사유 필수
- [ ] 서버 기준 최초 누락 판별, 잠금, stale-write 차단, 중복 저장 방지
- [ ] 기존 근태 보정 화면에 조건부 사유와 충돌 안내 연결
- [ ] 앱/관리자에서 corrected 상태를 출퇴근 완료로 인식
- [ ] 실제 Auth/Data API 회귀: 일반직원/기술관리자/비활성 계정/권한 시뮬레이션 차단

### B. 운영팀장 편집표
Tabulator를 편집표 계층에만 도입한다. 기존 서버 규칙을 표 라이브러리로 옮기지 않는다. 정확한 버전/라이선스/공급망 검증 후 정적 자산을 동일 출처로 제공한다.
- [ ] 날짜, 직원, 출근/퇴근, GPS/수기 출처, 오류/저장상태
- [ ] 셀 편집 실패 시 입력 보존 및 새로고침/재시도
- [ ] 실제 로딩된 그리드에 대해 브라우저 입력 테스트

### C. 일일 확정본 및 급여용 조회
- [ ] 원본/보정 reference와 직원 UUID를 가진 불변 일일 snapshot
- [ ] 확정 후 변경은 재확정 필요 표시, v1은 보존하고 v2 추가
- [ ] 미기록을 자동 결근/0시간으로 바꾸지 않음; 미해결 항목은 명시
- [ ] 퇴사/계정 변경 후에도 이미 확정한 과거 자료 조회 가능
- [ ] 보호된 기간별 확정본 조회, revision 및 미확정/빠진 날짜 명시
- [ ] 출퇴근 간 경과시간과 급여 인정시간을 구분; 임의 휴게시간/유급시간 계산 금지

## 이번 첫 PR의 경계
A를 먼저 구현·검증한다. B/C는 같은 #247에서 이어가며 A만으로 1차 전체 완료라고 보고하지 않는다. 과거 출근부의 '저장'과 새로 만들 일일 '확정'을 혼동하지 않는다.
CLI로 생성한 신규 migration만 사용하며 기존 적용 migration은 편집하지 않는다. 후보 SQL은 검증 workflow가 `supabase migration new`로 파일을 생성하고 clean replay/pgTAP/Auth를 수행한 뒤 영구 migration으로 승격한다.

## 운영 적용과 검증
코드 존재/빌드 성공/실기기 성공/Production 적용은 별도 상태다. 실제 Galaxy 동작, 장애 시 수기 대체, 확정본 복구 검증이 없는 상태를 실운영 완료라고 부르지 않는다.
main merge, Production migration, Play 공개배포, Edge Function 배포 및 지급/송금/급여월잠금은 이번 개발 승인에 포함되지 않는다.
