# 공지 관리 저장 검증·목록·보관함

기준: 2026-10-19 사용자 요청, 최신 main `cd30c275` (#490 포함).
운영총괄을 공통 UI 기준으로 하며 운영팀장 `promotion_lead`는 같은 모듈을 사용한다.

## 확인된 원인과 경계

- #446의 `list_manageable_notices` 운영팀장 분기는 `created_by=auth.uid()`만 반환한다. 타인 작성 전 직원 공개 공지가 빠지는 직접 원인이다.
- 저장 확인은 최대 200건 목록에 의존했고, 목록 실패에도 성공 메시지를 표시했다. 정확한 ID의 서버 내용·버전·사진을 대조하지 않았다.
- `operations-delete-controls`가 별도 쿼리 결과를 DOM 순번과 연결하고 보관 자료를 덧붙였다. 필터·정렬 이후 다른 ID를 보관할 위험이 있어, 공지 목록 소유자를 `notice-admin` 하나로 통일한다. 기존 복구·감사 도구는 공통 함수로 재사용한다.
- 수정 실패의 재현 가능한 원인: 2026-10-18 14:40~10-19 14:40 UTC Staging 집계에서 `save_notice` 5건 중 3건은 만료 JWT의 `401 / PGRST303` 거부였다. 사용자·토큰·공지 내용을 읽거나 로그에 기록하지 않고 상태/만료 여부만 집계했다. `app.js`는 진입 context에서만 refresh하고 업무 RPC는 갱신하지 않아, 편집 도중 만료되면 저장이 실행되지 않는다. 함수 정의는 최신 main과 일치하며 정상 인증의 동일 ID 수정은 격리 DB에서 성공한다. 이 만료 경로를 합성 운영총괄·운영팀장 JWT로 재현한다. 실제 신고의 개별 공지/계정과 로그를 연결했다고 주장하지 않는다.

## 최소 구현

1. 정확한 ID 조회 `get_manageable_notice`, 검색·총건수·offset 페이지 조회 `list_manageable_notices_page` 추가. 기존 제한 목록은 호환용으로 유지한다.
2. 읽기 전용 helper: 활성 notice.manage 보유 운영팀장은 본인 기존 관리 범위 + 이미 공개된 company 공지(종료 이력 포함)만 읽는다. 타인 초안·미래 예약·미허용 부서/개인/보관 자료는 제외한다.
3. 기존 수정 predicate, 저장·승인·사진 쓰기·보관·복구 RPC 및 RLS는 변경하지 않는다. Storage 읽기 predicate는 기존 함수 identity를 유지하면서 같은 읽기 경계만 확장한다.
4. 게시 중 / 예정·검토·초안 / 게시기간 종료를 최근 발행 시각(없으면 시작·작성 시각)으로 정렬한다. 종료 이력은 종료 시각 내림차순, 동률은 ID순이다. 시각은 KST로 표시하며 종료는 계산값일 뿐 상태를 변경하지 않는다.
5. 취소·사용 중지·명시적 보관은 같은 모듈의 보관함에서 조회한다. 기존 `archived_at`, `inactive`, `cancelled`를 사용하고 원본을 이동·삭제하지 않는다. 날짜 필터는 보관함에서 보관일 우선, 없으면 게시일 기준이다.
6. 저장 응답의 ID를 즉시 유지하고 최종 재조회 내용·버전·사진 일치 후에만 성공을 표시한다. 기존 게시 시작·종료의 초/밀리초도 보존한다. 기존 ID 수정 응답 유실은 동일 ID 재조회 후 확인하며 이미 반영된 본문을 재전송하지 않는다.
7. 새 공지 최초 저장 응답이 유실되어 ID를 얻지 못하면 자동 재시도/새 저장을 차단하고 입력을 유지한다. 제목 추정이나 자동 재게시를 하지 않는다. 서버 idempotency 계약 신설은 이번 범위에 포함하지 않는다.
8. 공통 RPC는 실행 전 JWT 검증에서 `401/PGRST303`으로 거부된 경우에만 기존 refresh로 갱신 후 원래 요청을 1회 재시도한다. 동시 요청은 갱신을 공유하고 계정 교체/로그아웃 중 늦은 응답은 세션을 복원하지 않는다. 권한 403/42501, DB/네트워크/5xx 오류는 재전송하지 않는다. RLS·역할·서버 승인 의미를 변경하지 않는다.

## 배포 안전

- Migration은 **Draft**이며 hosted Staging/Production 적용 전 사용자 승인이 필요하다. 함수만 변경하며 테이블·컬럼·실제 공지는 변경하지 않는다.
- 신규 RPC가 없는 Preview에서는 PGRST202에만 기존 최대 500건 목록으로 제한적 fallback하고, 전체 검색/타인 공지/보관 자료 미확인을 명시한다. 권한·통신 오류를 fallback으로 감추지 않는다.
- 고정 qa-preview를 교체하지 않는다. main 병합·Production 배포·환경변수 변경은 금지한다.
