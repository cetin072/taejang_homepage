# 홈페이지 사진 업로드 최적화

상태: 확정 — 2026-10-31 사용자 실행 지시. 검수와 필수 CI 통과 시 main 병합 승인. 강제 운영 배포는 제외하고 72시간 정규 배포 유지.

## 범위와 구조

사진 선택 → `photo-optimizer.mjs` → 결과 검증 → 기존 업로더.
기존 `notice-media.js`의 Image/Canvas 처리만 독립 모듈로 옮겨 보강한다. Auth·Storage·UI는 기존 소유자에 남는다. 외부 라이브러리·CDN·서비스·DB migration·권한 변경 없음. 모듈은 업로드 시 dynamic import하며 공개 홈페이지에는 추가하지 않는다.

적용: 홍보 직원/운영팀/운영총괄 공통 작성기, 운영총괄 홈페이지 직접 수정, 홈페이지 수정 요청, 공식 블로그 사진 가져오기, 공지 사진. 보존: 승인선·본인 Storage 경로·블로그 출처 marker·대표사진 선택·순서·중복 방지·공지 등록 결과 재조회. 기존 사진 일괄 교체/삭제·직원 인사사진·모바일 네이티브 공지 업로더는 의도적 제외.

## 처리 기준

- 원본 15MiB 이하, 40MP·긴 변 12000px 이하. 압축 바이트의 헤더를 먼저 검사한 뒤 브라우저로 디코딩한다. 폰카 EXIF는 브라우저의 방향 적용 Image 디코더에 맡긴다.
- 비율 유지, 확대 없이 긴 변 1600px, 목표 300~500KiB, 상한 1MiB. 별도 큰 히어로 사진 업로더는 현재 없다. 선택 대표사진/PHOTO 02~06 모두 같은 1600px 정책이며 직원 설정을 추가하지 않는다. 임의 1920px 프로필을 만들지 않는다.
- JPEG는 JPEG, PNG/WebP는 투명도를 유지하는 WebP 인코딩 우선. 미지원 브라우저가 PNG로 반환하면 실제 MIME/확장자를 사용한다. 기존 작은 사진은 재인코딩하지 않는다. 결과가 원본보다 커지면 기준을 만족하는 원본을 유지하거나 거부한다.
- GIF 및 animated PNG/WebP는 1600px·1MiB 이하만 원본 그대로 허용한다. 변환하지 않으며 초과 시 이유를 표시한다. HEIC 등 미지원 형식도 명확히 거부한다.
- 품질 0.86/0.78/0.70 최대 3회. 목표 용량 미달이라도 1MiB 이하인 결과를 허용하며 저화질을 강요하는 추가 반복은 하지 않는다.
- 공통 큐로 디코드/인코드 동시 실행 제한. 선택한 동일 File의 결과를 WeakMap으로 공유하며 실패한 최적화는 재시도 가능. 업로드 재시도는 원본으로 우회하지 않고 같은 non-upsert 키를 사용한다. 응답 소실 후 충돌(Asset Already Exists)은 성공으로 추정하지 않으며 기존 오류 경계를 유지한다.
- 순차 사진 처리, 실패한 남은 사진부터 재시도, 입력·완료 첨부 보존. 공지는 기존 저장 재시도/등록 확인을 유지하고 압축 실패의 원인도 표시한다.

## 검수·제한

`tests/photo-optimizer-browser.mjs`와 기존 홍보/공식 블로그/공지 브라우저 gate, platformStatic/publicHomepage, build 및 저장소 필수 CI로 확인한다. 새 검사는 실제 브라우저 인코더와 File, EXIF 8종, 투명도, GIF 원본 유지, 손상/미지원/초과/인코딩 실패, 401·실패 재시도, 실제 세 업로드 adapter의 body를 검사한다. 네트워크·RPC는 격리 fixture이며 운영 DB/Storage에 시험 사진을 쓰지 않는다. 승인된 저장소 사진 2종과 합성 이미지만 사용한다. 실제 Android/iOS 실기기 검수는 별도이며 Chromium PC/모바일 viewport 검수와 혼동하지 않는다.

실측 용량·해상도·MIME 및 화질 비교는 CI `photo-optimization-390-1440` artifact/PR에 기록한다. 실행하지 않은 검사를 통과로 기록하지 않는다. 이미 발생한 Storage/전송 사용량을 초기화하는 작업은 아니다.
