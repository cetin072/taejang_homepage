# 공개 홈페이지 콘텐츠 일괄 발행 설계 v1

> 상태: **확정 운영 원칙 반영 · 구현 전 설계 문서**
> 적용 범위: 홈페이지 자체 글, 외부 콘텐츠 카드, 공개용 이미지·썸네일, 고정 사진 슬롯, 정적 공개 발행본
> 구현 범위 아님: 이 문서는 화면·DB·migration·Supabase 연결·Netlify 설정 또는 Build Hook 호출을 수행하지 않는다.

## 1. 목적과 운영 원칙

공개 홈페이지는 Supabase 등 관리자 데이터베이스를 실시간으로 조회하지 않는다. 승인된 콘텐츠와 공개 승인된 이미지만 **고정된 공개 발행본**으로 생성하고, Netlify는 그 봉인된 정적 발행본만 조립·배포한다.

이 구조의 목적은 관리자·인증·DB·Storage 장애가 공개 홈페이지의 마지막 정상 화면을 바꾸거나 중단시키지 않게 하는 것이다. 새 발행이 실패하면 마지막 정상 공개본을 계속 제공한다.

`Netlify Build Hook`은 빌드를 시작하라는 신호일 뿐, DB에서 콘텐츠를 자동으로 읽어 오는 기능이 아니다. 따라서 Build Hook을 사용한다면 발행 서버가 먼저 공개 발행본을 완성·봉인하고 발행본 식별자를 만든 뒤에만 호출한다.

```mermaid
flowchart LR
  A[승인 콘텐츠·공개 이미지] --> B[발행 서버 검증]
  B --> C[봉인된 정적 발행본]
  C --> D[발행본 식별자]
  D --> E[Netlify Build Hook]
  E --> F[Netlify 정적 배포]
  F --> G[마지막 정상 공개본 지정]
```

발행 순서는 다음으로 고정한다.

1. 현재 유효하게 승인된 콘텐츠 revision만 조회한다.
2. 공개 승인·동의 확인을 마친 공개용 파생 이미지와 썸네일만 조회한다.
3. 공개 JSON·정적 데이터·공개 파일 manifest를 생성한다.
4. 형식·링크·이미지·중복·공개 제외 항목을 검증한다.
5. 검증 결과와 checksum을 포함한 발행본을 봉인한다.
6. 발행본 ID를 만든 뒤, 승인된 서버 경로에서만 Netlify Build Hook을 호출한다.
7. Netlify는 DB가 아니라 지정된 봉인 발행본만 조립·배포한다.
8. 배포와 공개 결과 확인이 모두 성공했을 때만 해당 발행본을 `last_known_good`으로 지정한다.

## 2. 범위와 용어

| 용어 | 의미 |
| --- | --- |
| 콘텐츠 | 홈페이지 자체 글 또는 외부 콘텐츠 카드의 논리 항목 |
| revision | 제목·본문·요약·미디어·외부 URL 등을 특정 시점에 고정한 검토 단위 |
| 공개용 이미지 | 원본과 분리된 웹용 파생 파일. 공개 승인·동의 확인을 거친 파일만 해당 |
| 발행 대기함 | 승인 완료 후 다음 정기 발행에 넣을 후보 목록 |
| 발행 회차 | 한 번의 정기 또는 긴급 발행으로 봉인된 공개본 단위 |
| 봉인 발행본 | 대상 revision·이미지 manifest·checksum·생성 시각을 고정해 이후 변경을 막은 결과물 |
| 마지막 정상본 | 배포와 공개 확인을 통과한 가장 최근 발행본 |

원본 사진·동의서 원문·검토 의견·내부 메모·계정 정보·감사 로그는 공개 발행본에 넣지 않는다. 공개 이미지에는 동의 사실의 참조값만 내부 메타데이터로 두며, 동의서 원문 자체를 공개하지 않는다.

## 3. 승인 책임과 콘텐츠 구분

### 3.1 일반 콘텐츠: 홍보팀장 최종 책임

일반 콘텐츠의 게시 여부는 홍보팀장이 최종 결정한다. 홍보팀장 승인 뒤 운영총괄이나 대표이사에게 일괄 추가 상신하지 않는다.

홍보팀 직원은 자체 글 작성, 외부 링크·사진·썸네일 등록, 임시저장, 게시 요청, 보완 요청을 받은 콘텐츠 수정까지 수행한다. 직원은 게시 승인, 발행 대기 확정, Production 발행, 강제 비공개, 이전 정상본 복구, 권한 변경을 수행할 수 없다.

홍보팀장은 사실관계, 문구, 제목·요약·썸네일, 외부 링크, 개인정보 노출, 사진 공개동의를 확인하고 수정 요청·반려·승인·발행 대기함 편성·주간 발행 대상 확정을 수행한다. 일반 콘텐츠의 게시 여부에 대한 최종 책임은 홍보팀장에게 있다.

### 3.2 일반 콘텐츠 범위

다음은 원칙적으로 홍보팀장 최종 승인 범위다.

- 네이버 블로그·유튜브·인스타그램 등 SNS 링크와 언론보도 원문 링크의 일반 등록
- 일반 회사소식, 일터 이야기, 민화 작업 기록, 포장·검수 작업 기록, 환경정비 수행 기록
- 행사 안내·후기, 제품·행사 관련 일반 소식, 기존 사업의 일반 협력·참여 안내
- 공개 승인된 현장 사진, 아카이브 썸네일, 홈페이지 사진 슬롯의 일반 사진 교체
- 기존 게시물의 오탈자·단순 문구 수정

기본 흐름은 다음과 같다.

```text
작성 중 → 게시 요청 → 홍보팀장 검토
→ 수정 요청 또는 반려
→ 홍보팀장 승인 → 발행 대기 → 주간 발행 목록 확정
→ 최고관리자 Production 발행 → 게시됨
```

### 3.3 일반·중요 콘텐츠의 분류 보류

일반 콘텐츠와 중요 콘텐츠의 경계가 애매할 때 홍보팀장은 임의로 일반 콘텐츠로 확정하지 않는다. 다음 흐름으로 처리한다.

```text
홍보팀장 판단 보류 → 운영총괄 검토 요청
→ 운영총괄이 일반 또는 중요 콘텐츠로 최종 분류
→ 일반 콘텐츠면 홍보팀장 승인 흐름으로 복귀
→ 중요 콘텐츠면 운영총괄 결재 흐름으로 진행
```

분류 결정, 결정 사유, 요청자와 결정 시각은 감사 로그에 남긴다. 이 절차는 운영총괄이 일반 콘텐츠를 일상적으로 승인한다는 뜻이 아니다.

### 3.4 홍보팀장 부재 시 사전 지정 대리 승인

홍보팀장 부재 시 누구나 임의로 승인할 수 없다. 운영총괄이 사전에 지정한 대리 승인자만 지정된 기간에 한해 홍보팀장 승인 권한을 사용할 수 있다.

대리 승인 지정에는 대리 승인자, 지정자, 지정 사유, 권한 시작일·종료일을 기록한다. 대리 승인자가 처리한 콘텐츠, 승인 결과와 시각도 별도로 감사 로그에 남긴다. 권한은 종료일에 자동 만료되며, 연장·변경도 새 지정 기록과 감사 로그를 남긴다.

### 3.5 중요 콘텐츠: 운영총괄 상신

다음은 일반 콘텐츠로 처리하지 않고 홍보팀장 검토 뒤 운영총괄에게 상신한다.

- 대표이사 명의의 공식 입장
- 새로운 모회사 참여 발표, 주요 협약 발표, 중요한 신규 사업 발표
- 중요한 채용정책 또는 대외정책 발표, 회사 핵심 사업 방향 변경
- 홈페이지 첫 화면 핵심 메시지 또는 회사 주요 사업 설명 변경
- 대외적으로 민감한 보도자료, 법적·평판상 위험 가능성이 있는 콘텐츠
- 주요 기업·기관과의 관계를 공식적으로 발표하는 콘텐츠
- 홍보팀장이 중요 검토가 필요하다고 판단한 콘텐츠

대부분의 중요 콘텐츠는 운영총괄이 최종 결재한다.

```text
홍보팀 직원 작성 → 홍보팀장 검토 → 운영총괄 상신
→ 운영총괄 승인 또는 반려 → 발행 대기 → 주간 발행 목록 확정
→ 최고관리자 Production 발행 → 게시됨
```

### 3.6 대표이사 검토는 예외적 상신

대표이사는 모든 콘텐츠를 검토하지 않는다. 운영총괄이 대표 검토가 필요하다고 지정한 중대 안건만 대표이사에게 상신한다.

대표 검토 대상 예시는 대표이사 명의 공식 인사말·공식 입장, 새로운 모회사 참여, 중대한 협약·투자·사업 발표, 회사 평판에 큰 영향을 줄 대외 발표, 법적·정책적 의미가 큰 콘텐츠다.

```text
홍보팀장 검토 → 운영총괄 검토 → 대표 검토 필요 지정
→ 대표이사 상신 → 대표이사 승인 또는 반려
→ 발행 대기 → 주간 발행 목록 확정
→ 최고관리자 Production 발행 → 게시됨
```

운영총괄이 대표 검토 대상으로 상신하지 않은 콘텐츠는 대표이사 대시보드의 기본 결재 목록에 표시하지 않는다. 이는 대표이사의 전체 열람 가능 범위와 별개다.

## 4. 상태 모델: 승인과 실제 발행의 분리

콘텐츠 승인 상태와 실제 발행 상태를 하나의 컬럼으로 섞지 않는다. 승인되었다고 바로 공개되는 것이 아니며, 공개되었다고 과거의 승인 이력이 사라지는 것도 아니다.

### 4.1 revision 검토·승인 상태

아래 상태는 **특정 revision의 검토와 승인선**을 나타낸다.

| 상태 | 의미 | 다음 가능 상태 |
| --- | --- | --- |
| `draft` | 작성·임시저장 중 | `submitted` |
| `submitted` | 홍보팀장 검토 요청됨 | `changes_requested`, `rejected`, `team_lead_approved`, `escalated_to_operations` |
| `changes_requested` | 보완 요청됨 | `draft`, `submitted` |
| `rejected` | 해당 revision 반려 | 새 `draft` revision |
| `team_lead_approved` | 일반 콘텐츠의 홍보팀장 최종 승인 | `queued_for_release` |
| `escalated_to_operations` | 중요 콘텐츠를 운영총괄에게 상신 | `changes_requested`, `rejected`, `operations_approved`, `escalated_to_ceo` |
| `operations_approved` | 운영총괄 최종 결재 | `queued_for_release` |
| `escalated_to_ceo` | 운영총괄이 대표 검토 대상으로 지정 | `changes_requested`, `rejected`, `ceo_approved` |
| `ceo_approved` | 대표이사 검토 완료 | `queued_for_release` |

일반 콘텐츠는 `team_lead_approved`에서 바로 `queued_for_release`로 갈 수 있다. 중요 콘텐츠만 `escalated_to_operations`를 사용하고, 대표 검토 대상만 `escalated_to_ceo`를 사용한다.

승인된 revision을 편집하면 새 revision을 만들고 다시 검토한다. 과거 승인 기록은 보존하되, 발행은 해당 revision의 **현재 유효 승인 상태**만 인정한다.

### 4.2 발행 대기·발행 상태

아래 상태는 revision 검토 상태와 별도로 **공개 발행 과정**을 나타낸다.

| 상태 | 의미 |
| --- | --- |
| `not_queued` | 아직 발행 대기 대상이 아님 |
| `queued_for_release` | 유효 승인 후 발행 대기함에 있음 |
| `included_in_release` | 특정 봉인 발행 회차에 포함됨 |
| `published` | 해당 revision이 마지막 정상 공개본에 포함되어 공개 중 |
| `hidden` | 공개를 중단했으나 콘텐츠·revision·사유는 보존 |
| `archived` | 운영 목록·기본 노출에서는 제외하고 기록 보존 |
| `release_failed` | 생성·봉인·배포·공개 확인 실패. 기존 공개 상태는 유지 |

`hidden`과 `archived`는 콘텐츠의 공개 운영 상태이며, revision의 승인 이력과 다르다. 콘텐츠의 soft delete는 별도 보존 정책으로 관리하며, 이 문서의 강제 비공개를 물리적 삭제로 처리하지 않는다.

## 5. 권한표

| 역할 | 허용 업무 | 기본적으로 허용하지 않는 업무 |
| --- | --- | --- |
| `promotion_staff` | 작성, 업로드, 임시저장, 게시 요청, 보완 요청 대응 | 승인, 발행 대기 확정, Production 발행, 강제 비공개, 복구, 권한 변경 |
| `promotion_lead` | 일반 콘텐츠 최종 승인, 수정 요청, 반려, 발행 대기함 편성, 주간 발행 대상 확정, 중요 콘텐츠 운영총괄 상신 | Production 발행 실행, 긴급 발행, 강제 비공개, 이전 정상본 복구, 권한 변경 |
| `operations_manager` | 중요 콘텐츠 최종 결재, 일반·중요 경계 최종 분류, 대표 검토 필요 지정·상신, 홍보팀장 부재 시 대리 승인자 사전 지정, 필요 시 전체 콘텐츠 열람 | 일반 콘텐츠의 일상 승인에 기본 참여, 긴급 발행·강제 비공개·복구 직접 실행 |
| `ceo` | 운영총괄이 상신한 중대 안건만 검토 | 일반 콘텐츠 승인 목록 기본 노출, 직접 발행, 강제 비공개, 복구 |
| `super_admin` | 긴급 발행, 강제 비공개, 이전 정상본 복구, 발행 잠금 해제, 시스템 설정, 권한 관리 | 사유·감사 로그 없는 모든 중요 작업 |

모든 역할은 계정 상태가 `active`일 때만 허용된 작업을 수행한다. `suspended`·`departed` 계정은 작성·수정·승인·업로드·발행을 즉시 할 수 없고, 과거 콘텐츠·승인·감사 기록은 보존한다. 마지막 active `super_admin` 보호는 기존 Phase 1A 보안 기준을 따른다.

## 6. 정기 주간 발행

Production 발행은 기본적으로 주 1회 일괄 수행한다. 승인된 콘텐츠는 즉시 공개하지 않고 발행 대기함에 모은다.

기본 발행 요일과 시각은 **매주 금요일 오후 4시**다. 시스템 설정값으로 변경할 수 있게 설계하되, MVP 기본값은 이 운영 결정을 사용한다. 승인된 발행 대상이 없으면 빈 Production 배포를 실행하지 않는다.

### 6.1 발행 대기함 표시 항목

- 이번 주 발행 대상, 다음 발행 예정일·시각, 콘텐츠 유형과 승인자
- 중요 콘텐츠 여부, 대표 검토 여부, 사진·썸네일 포함 여부
- 공개동의 확인 상태, 보류·제외 항목과 사유, 발행 예상 건수
- 회차 번호, 대상 확정 시각, 확정자, 대상 revision ID

### 6.2 주간 회차와 확정 규칙

- 회차 번호는 예: `W2026-31`처럼 연도와 주차를 포함하되, 정확한 표기 규칙은 시스템 설정으로 관리한다.
- 홍보팀장이 대상을 확정하면 `queued_for_release` revision만 해당 회차의 후보가 된다.
- 발행 서버는 확정본을 읽기 전용 snapshot으로 봉인하고 `included_in_release`로 표시한다.
- 주간 목록이 봉인된 뒤 새로 승인되거나 일반적인 수정이 발생한 콘텐츠는 해당 회차에 자동 삽입하거나 다시 넣지 않고 다음 주 대기함으로 이월한다.
- 봉인 뒤 다음 사유만 예외로 처리한다: 개인정보 노출, 미동의 사진, 행사 일정·장소 오류, 채용·접수 마감 정보 오류, 중대한 사실 오류, 법적·보안상 즉시 수정이 필요한 경우.
- 예외 수정은 `super_admin`이 긴급 사유를 기록한 뒤 8절의 긴급 발행으로 처리한다. 일반 수정은 다음 주 발행 대상으로 남기고, 필요하면 새 revision을 승인받는다.
- 발행 직전에는 현재 유효 승인, 공개동의, 공개 파일 존재, URL·JSON·checksum, 같은 콘텐츠의 중복 포함 여부를 다시 검증한다.
- 완료 후 성공한 revision은 `published`로, 제외된 항목은 대기함 또는 보류 목록으로 명확히 정리한다. 같은 콘텐츠·revision은 같은 회차에 한 번만 포함할 수 있다.

### 6.3 목록 확정과 실제 실행의 분리

발행 목록 확정과 Production 발행 실행은 서로 다른 권한이다. MVP 초기 운영은 다음처럼 확정한다.

```text
홍보팀장: 주간 발행 콘텐츠 목록 최종 확정
시스템 최고관리자: 실제 Production 발행 실행
```

홍보팀장이 일반 콘텐츠의 최종 승인자여도 긴급 배포, 복구, 발행 잠금 해제 권한까지 갖지는 않는다. 운영총괄은 중요 콘텐츠 결재·대표 상신을 담당하되 일상 발행 실행 권한을 자동으로 갖지 않는다.

후속 단계에서는 운영 안정성과 감사 로그를 확인한 뒤 예약 자동 발행 또는 홍보팀장 직접 정기 발행을 재검토할 수 있다. 어떤 방식이든 사람이 확정한 봉인 회차, 동일한 검증, 감사 로그와 실패 처리 규칙을 우회할 수 없다.

## 7. 발행 안전장치와 실패 처리

발행 작업은 다음 안전장치를 유지한다.

- 단일 발행 잠금과 잠금 보유자·만료 시각 기록
- 요청별 `idempotency key`와 동일 발행본 중복 배포 방지
- 대상 revision·공개 이미지 manifest·checksum을 포함한 sealed release
- 재시도 횟수 제한과 재시도 사유 기록
- 승인되지 않은 revision·공개 승인되지 않은 이미지의 자동 제외
- 공개 발행본 무결성 검증과 배포 후 결과 확인
- 마지막 정상 공개본 유지, 실패 기록, 이전 정상본 복구

발행 실패는 봉인·Hook 호출·Netlify 배포·배포 결과 검증 중 어느 단계에서든 발생할 수 있다. 실패한 새 발행본은 `last_known_good`을 바꾸지 않으며, 이전 공개 URL과 정적 파일을 유지한다. 오류 기록에는 비밀값·토큰·동의서 원문·민감한 본문을 남기지 않는다.

## 8. 긴급 발행, 강제 비공개, 복구

### 8.1 긴급 발행

긴급 발행은 행사 일정·장소의 긴급 변경, 채용·접수 마감, 공개된 중요 오류 정정, 공식 발표 시각 대응, 법적 문제의 즉시 정정, 개인정보·미동의 사진 문제의 긴급 수정처럼 정기 발행을 기다릴 수 없는 예외에만 사용한다. 단순히 빨리 공개하고 싶다는 이유는 허용 사유가 아니다.

긴급 발행은 `super_admin`만 실행한다. 실행 전 대상 콘텐츠·현재 유효 승인·공개 파일을 다시 검증하고, 다음을 감사 로그에 남긴다.

- 긴급 사유, 요청자, 승인자, 실행자, 대상 콘텐츠·revision
- 기존 발행본, 새 발행본, 실행 시각, 결과, 실패 시 조치

### 8.2 강제 비공개

개인정보·장애·건강정보 등 민감정보 노출, 사진 공개동의 누락·철회, 계약상 비공개 정보, 잘못된 회사·기관명, 중대한 사실 오류, 저작권·초상권 문제, 보안정보·내부자료 노출, 즉각적 법적·평판 위험일 때만 사용한다.

강제 비공개는 `super_admin`만 실행한다. 콘텐츠를 물리적으로 즉시 삭제하지 않고 기존 공개본, 비공개 사유, 실행자·실행 시각, 관련 승인자, 복구 가능 여부, 감사 로그를 보존한다. 필요한 경우 비공개 상태를 반영한 새 봉인 발행본을 긴급 발행한다.

### 8.3 이전 정상본 복구

배포 후 화면 깨짐, 메뉴·링크·이미지 대량 오류, 승인되지 않은 콘텐츠 포함, 문의폼 등 주요 기능 오류, 개인정보·보안 문제, 봉인 발행본과 실제 배포 결과 불일치가 발견되면 이전 정상본 복구를 수행할 수 있다.

복구는 `super_admin`만 실행하며, 복구 대상 발행본·문제 발행본·사유·실행자·시각·결과·후속 조치를 기록한다. 복구는 콘텐츠 DB를 임의로 되돌리는 작업이 아니라, 검증된 이전 공개 발행본을 다시 활성화하는 절차다.

## 10. 외부 콘텐츠 카드

네이버 블로그, 유튜브, 인스타그램, 언론보도와 기타 외부 링크는 `소식·기록`에 외부 콘텐츠 카드로 등록한다. 카드는 새 탭에서 원문으로 이동한다.

필수 관리 항목은 출처, 원문 URL, 제목, 요약, 썸네일·대체텍스트, 카테고리, 원문 게시일, 홈페이지 노출일, 상단 고정, 공개 상태, 작성자, 승인자, 수정일, 발행일, 숨김 상태, 보관 상태다.

URL 자동 분석은 시도할 수 있지만 실패가 등록을 막으면 안 된다. 제목·요약·썸네일·게시일·출처 직접 입력과 자동 분석 결과 수정은 항상 제공한다. 네이버 블로그와 인스타그램의 외부 접근 제한을 고려해 수동 입력을 기본 대체 흐름으로 둔다.

서버 측 URL 분석을 도입할 경우 SSRF 차단, 도메인 allow-list, 내부 IP 차단, redirect 횟수·응답 크기·요청 시간 제한, 파일 유형 검증을 적용하며 실패하면 수동 입력으로 전환한다.

## 11. 발행 데이터와 감사 기록

최소 논리 구조는 기존 Phase 1A의 콘텐츠·revision·현재 유효 승인·감사 모델을 보강한다. 실제 테이블·migration은 별도 승인 작업에서 결정한다.

| 논리 항목 | 핵심 값 |
| --- | --- |
| `release_batches` | 회차 번호, 유형(정기/긴급/복구), 확정자·확정 시각, 실행자, 상태, idempotency key |
| `release_items` | 회차, 콘텐츠 ID, revision ID, 포함·제외 상태, 제외 사유, 중복 방지 키 |
| `sealed_releases` | 발행본 ID, manifest, checksum, 생성 시각, Build Hook 요청 식별자, 배포 결과 |
| `media_assets` | 원본·공개 파생 파일 관계, 공개 승인·동의 메타데이터, 대체텍스트, 크롭, checksum |
| `release_history` | 마지막 정상본 여부, 이전·다음 발행본 관계, 복구·비공개 영향 |
| `audit_logs` | 행위자, 대상, 사유, 결과, 시각. 비밀값·민감 원문 제외 |

감사 로그는 승인, 수정 요청, 반려, 일반·중요 분류 결정과 사유, 대리 승인 지정·자동 만료·대리 승인 결과, 대기함 편성·확정, 포함·제외, 봉인, 발행 시작·성공·실패, 긴급 발행, 강제 비공개, 복구, 잠금 해제를 모두 기록한다.

## 12. MVP와 후속 단계

### MVP에 포함

- 자체 글 작성·수정·게시 요청, 외부 링크 수동 등록, 썸네일 직접 업로드
- PHOTO 01~08 고정 사진 관리와 각 공개 콘텐츠 대표사진의 공개동의 확인
- 홍보팀장 일반 콘텐츠 승인, 중요 콘텐츠 운영총괄 상신, 대표 검토 선택 상신
- 발행 대기함, 주간 발행 대상 확정, `super_admin`의 실제 Production 발행 실행, 고정 공개 발행본 생성 설계
- 운영총괄의 일반·중요 경계 최종 분류와 기간 자동 만료 대리 승인 지정
- Netlify Build Hook 연계 설계, 발행 성공·실패 기록, 마지막 정상본 유지
- 긴급 발행, 강제 비공개, 이전 정상본 복구, 감사 로그

위 MVP 항목 중 실제 DB·인증·Storage·Hook 연결은 이 문서로 구현된 것이 아니다. 우선 실제 운영 연결의 승인·보안 경계를 검증한 뒤 단계적으로 착수한다.

### 후속 단계

| 항목 | 미루는 이유 |
| --- | --- |
| URL 자동 분석 고도화·유튜브 API 수집 | 외부 접근 제한과 SSRF·API 운영 위험 검증 필요 |
| 자동 썸네일 추천 | 정확도·저작권·운영 검토 필요 |
| 예약된 주간 자동 발행 또는 홍보팀장 직접 정기 발행 | MVP 운영 안정성과 감사 로그를 확인한 뒤 책임 분리·실패 대응 기준을 재검토 |
| 자동 리사이즈·WebP 변환·크롭 미리보기 | 운영 편의성은 높지만 MVP 보안·승인보다 후순위 |
| PC·모바일 자동 화면 점검·배포 완료 자동 확인 | 배포 환경과 검사 기준을 먼저 안정화해야 함 |
| 통계·월별 운영 보고 | 공개·승인·발행 흐름이 안정화된 뒤 운영 데이터로 설계 |

## 13. 기존 설계와의 관계

- [Phase 0 기술 설계](ADMIN_PHASE0_TECHNICAL_ARCHITECTURE.md)의 정적 발행, 마지막 정상본, 원본·공개 파일 분리 원칙을 유지한다.
- [Phase 1A 보안 기술 검증](ADMIN_PHASE1A_SECURITY_SPIKE.md)의 active 계정 확인, 현재 유효 승인, 단일 공개 revision, 감사 로그 보호, 마지막 최고관리자 보호를 유지한다.
- [Phase 1B 콘텐츠 중심 운영·UX 프로토타입](ADMIN_PHASE1B_CONTENT_WORKFLOW.md)의 자체 글·외부 카드·수동 입력·미리보기 흐름을 유지하되, 실제 운영 연결 시 이 문서의 역할별 승인선과 주간 발행 흐름을 적용한다.
- 기존 문서의 단순 `approved → publishing → published` 상태는 일반적인 초기 설계다. 공개 콘텐츠 운영에서는 이 문서의 revision 승인 상태와 발행 상태 분리를 최신 세부 기준으로 사용한다.
