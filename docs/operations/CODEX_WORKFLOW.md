# 태장 AI 개발 작업 절차

ChatGPT·Codex 등으로 이 저장소에서 작업할 때 필요한 실행 절차다. 상시 기준은 [AGENTS.md](../../AGENTS.md)이며, 이 문서는 실행·검수·복구 절차가 필요한 때만 읽는다. 다른 프로젝트에는 그 프로젝트의 지침·QA 주소·승인 구조를 적용한다.

## 1. 시작: 현재 작업에 필요한 문맥만 확인

- 로컬에서는 `git fetch origin` 후 저장소, 최신 `origin/main`, 현재 branch와 working tree를 확인한다. 커넥터만 사용할 때는 원격 기준 commit/branch/PR을 확인하고 확인하지 못한 로컬 상태를 구분한다.
- 기본 읽기는 `AGENTS.md` + 현재 요청/Issue + 인접 파일·관련 테스트다. 기존 작업이면 기존 branch/Draft PR과 최신 review를 읽고 이어간다. 새 작업이며 대응 Issue/branch/PR이 없을 때만 최신 기준 브랜치에서 새 흐름을 만든다.
- 새 기능·목적·범위 결정은 `PROJECT_CHARTER.md`와 확정 planning/Goal을 추가한다. 단순 버그·문구·스타일 작업마다 헌장 전문을 다시 읽지 않는다. 모델 정책은 선택이 애매하거나 위험도 재평가가 필요할 때 읽는다.
- 문서 우선순위는 읽기 순서가 아니다. 공통 안전 원칙 → 프로젝트 헌장·확정 기획 → 현재 승인된 Goal/Issue를 판단 기준으로 삼고, 실제 구현·검증 상태는 commit/PR/CI에서 확인한다. 충돌 시 관련 원문과 승인 기록을 확인하며 중요한 계약 변경은 승인 없이 진행하지 않는다.
- 새 ChatGPT 대화나 다른 AI 도구가 GitHub 파일을 자동 로딩한다고 가정하지 않는다. 작업 시작 지시에 “대상 저장소의 AGENTS.md를 먼저 확인하고 관련 문서만 읽는다”는 진입점을 둔다. GitHub 연결·파일 접근·도구별 적용 범위는 실제로 확인한다.

## 2. 계획·구현·반복

- 현재 Issue에 과제, 변경 금지 범위, 확인 방법, 끝나는 조건을 정한다. 새 기능·범위 결정은 `docs/planning/PLANNING_RECORD_SYSTEM.md`에 따라 관련 확정 기획에 기록한다. 검토 중인 아이디어를 확정 구현으로 취급하지 않는다.
- 현재 코드와 검증된 구현을 먼저 재사용한다. 요청 밖의 리팩터링, 디자인 전면 변경, 새 최상위 디렉터리·자산 체계·서비스를 끼워 넣지 않는다. 불가피한 구조 변경은 영향과 이유를 제시해 판단받는다.
- 승인 범위의 구현, targeted test, 문법·build·lint, 작은 오류 수정, 회귀 테스트, Draft PR·문서 갱신은 스스로 이어간다. 같은 실패를 이유 없이 반복하거나 모델만 올려 승인 게이트를 우회하지 않는다.
- Codex 지시에는 현재 작업에 맞는 `권장 모델`, `권장 추론`, `선정 이유`를 짧게 남긴다. 구체 조합은 `MODEL_SELECTION_POLICY.md`를 따른다. Goal/Issue가 충분히 명확하면 다음 지시는 `계속해`처럼 짧게 한다. 실제 도구에 없는 모델이나 변경 권한을 있다고 보고하지 않는다.
- 원본·기존 미커밋 변경의 출처와 목적을 확인하고 이번 작업에 임의 포함하지 않는다. 사용하지 않는 코드·자산·중복 구현은 관련 범위에서만 정리한다.

## 3. 사람 판단과 안전 경계

`AGENTS.md`의 승인 경계를 그대로 적용한다. 특히 핵심 아키텍처, 확정 기획·승인선, 데이터·상태·Auth/RLS·권한 의미, 중요한/파괴적 migration, 실제 사용자 계정·민감정보, 새 외부 서비스·추가 비용, 운영 URL·환경변수·배포 설정은 실행 전에 필요한 승인을 확인한다.

Ready for review, `main` 병합, Production Supabase 변경·배포는 구현 완료와 구분한다. 승인된 TEST-only 작업도 운영 데이터 쓰기 권한을 뜻하지 않는다. 비밀값은 코드·문서·로그에 넣지 않는다. 권한 오류·보안규칙을 우회하지 않으며 무승인 force push를 하지 않는다.

## 4. 검사: 증거와 적용 범위 구분

변경 직후에는 `git diff --check`와 전체 변경 diff, 직접 관련된 문법·링크·경로·targeted test를 확인한다. 완료/중요 Gate 직전에는 필요한 회귀·CI·산출물 검사를 추가한다. 입력·코드·환경이 그대로인 hosted mutation·고비용 검증은 근거 없이 재실행하지 않는다.

사용자에게 실제 화면·기능 검수를 요청할 때는 [공통 Preview QA Gate](https://github.com/cetin072/ai-development-system/blob/main/docs/PREVIEW_QA_GATE.md)를 적용한다. 필수 `User Acceptance Ready`를 포함한 해당 작업의 필수 체크를 우회하지 않는다. 테스트별 측정 범위를 구분하며 소스 문자열 검사나 fixture 존재를 실제 로그인·저장·새로고침·화면 안정성 검증으로 보고하지 않는다.

사용자가 발견한 기계적 버그는 원인 수정과 함께 가능한 재현 테스트·fixture·경로·안정성 검사를 남긴다. 필수 검증 실패·미확인이면 사용자 검수 요청을 보류하고 막힌 항목을 기록한다.

웹 동작·빌드 산출물을 바꾸지 않는 순수 분석·문서 작업은 문서 diff·참조·규칙 정합성을 검토한다. 이런 작업에 웹 화면 검수나 QA 브랜치 배포를 요청하지 않는다. 실행 코드·설정·생성 산출물이 함께 바뀌면 관련 runtime Gate를 적용한다. 문서 전용이라는 이유로 저장소 필수 CI나 병합 승인을 해제하지 않는다.

## 5. 고정 사용자 웹 QA 갱신

사용자 웹 검수 주소: **https://qa-preview--taejang-homepage.netlify.app**

기존 Netlify `taejang-homepage` 프로젝트의 `qa-preview` 브랜치 배포를 사용한다. 별도 Netlify 프로젝트·Production 설정을 새로 만들거나 바꾸지 않는다. PR별 Deploy Preview는 개발·자동검증용이며 사용자 기본 검수 주소로 대체하지 않는다.

1. **대상 고정:** 검수 대상 PR, 정확한 HEAD SHA, 현재 `qa-preview` SHA와 배포 상태를 확인한다. 관련 자동검증, diff·회귀·대표 사용자 흐름을 먼저 확인한다. 필수 체크가 남으면 완료로 보고하지 않는다.
2. **동시 작업 보호:** 현재 QA를 누가 어떤 PR 검수에 쓰는지 공유 Issue/PR 기록을 확인한다. 다른 검수가 진행 중이거나 상태가 불명확하면 임의 교체하지 않는다. 이전 QA SHA와 새 대상·교체 이유를 기록한다. 이전 SHA는 코드 복구 기준일 뿐 DB·계정·데이터를 되돌리는 명령이 아니다.
3. **안전한 동기화:** `qa-preview`를 확인한 대상 HEAD와 일치시킨다. 갱신 직전 원격 SHA가 읽었던 값인지 다시 확인한다. 다른 작업이 끼었거나 non-fast-forward 교체가 필요하면 멈추고 조정·명시 승인을 받는다. 무조건 force push, QA에 임의 기능 커밋 추가, 여러 PR의 조용한 혼합은 하지 않는다.
4. **실제 배포 검증:** 브랜치 갱신 성공만으로 끝내지 않는다. Netlify가 그 SHA를 `Ready`로 배포했는지, 고정 URL의 실제 자산·필요한 API 경로와 런타임 설정이 승인된 Staging을 사용하는지 확인한다. 필요한 migration/function 계약도 확인하되 Production/실사용 데이터 변경은 별도 승인 경계를 따른다. 이전 배포나 운영 DB가 연결돼 있으면 사용자 검수를 요청하지 않는다.
5. **인계:** Issue/PR에 QA URL, 검수 대상 PR/HEAD, 실제 배포 ID·SHA, 환경 확인, 실행한 검사와 남은 사람 확인을 기록하고 같은 고정 URL을 사용자에게 전달한다. 새 수정이 생기면 다시 검증한다. SHA가 다르면 “최신 반영 완료”라고 하지 않는다.

필수 Gate 미확인 시 “고정 QA 갱신 미완료”와 원인을 보고한다. PR별 URL로 바꿔 알려서 동기화 누락을 감추지 않는다. QA 갱신은 사용자 최종 승인이나 `main` 병합·Production 배포를 뜻하지 않는다.

## 6. GitHub 게시·PC 이동·복구

- 완료한 변경은 목적에 맞게 commit/push하고 기존 Draft PR을 갱신한다. 원격 도구로 작성할 때도 기준 SHA와 변경 범위를 확인한다. PR에는 Issue, 목적, 변경 파일, 관련 기획, 검사 결과, 남은 blocker·승인을 남긴다.
- 다른 PC로 이동하기 전 가능한 최소 commit/push와 Draft PR을 남긴다. GitHub Issue·branch·commit·PR을 공유 상태로 사용하며, 새 PC에서 과거 대화를 복원하려고 전체 저장소·모든 문서를 다시 읽지 않는다.
- 작업 내용, 상태, 검증 증거는 실제로 확인한 범위만 보고한다. push/PR 실패 시 단계·오류·HTTP 코드(있는 경우)·branch·remote·변경 파일을 기록하되 비밀값을 출력하지 않는다.
- 코드의 `main` 병합과 Production 릴리스는 별개다. 현재 배포 게이트·설정을 확인하고 사용자가 승인한 반영 범위만 실행한다. 과거 대화의 “병합하면 즉시 배포”를 현재 사실로 추정하지 않는다.

## 7. Goal과 완료 보고

Goal은 Issue를 대체하지 않는다. 장기 제품 방향은 Epic/Goal과 확정 planning, 현재 구현 범위는 Issue, 실제 결과물은 Draft PR에 둔다. Goal에는 목적·제약·자율범위·검증·반복 중단 조건만 두고 작업별 필드·RLS 조건·TEST 데이터는 현재 Issue에 둔다.

완료 보고는 PR/최종 HEAD, 핵심 변경·파일, 적용 기획과 구현/부분 구현/후속/제외 대조, 실행한 테스트·CI·QA 결과, 미확인 항목, 다음 승인 단계로 정리한다. 필수 검증과 blocker를 확인한 구현 완료 후보와 사용자 승인·병합·운영 반영 완료를 구분한다. 독립 검수는 별도 검수자/문맥으로 실제 수행했을 때만 그렇게 표기한다.
