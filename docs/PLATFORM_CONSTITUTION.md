# 태장 홈페이지·업무플랫폼 확장형 아키텍처 개발 헌법 v1.0

> 상태: 상위 아키텍처 원칙
> 적용 대상: 태장 공개 홈페이지, 태장 내부 업무플랫폼, 향후 공통 Platform/Shared/Core 추출 작업
> 핵심 문장: **현재 태장을 제대로 만드는 것을 우선한다. 그러나 태장만 만들 수 있는 구조로 만들지는 않는다.**

## 1. 목적

현재 개발 중인 태장 홈페이지와 백엔드 업무플랫폼은 태장 한 회사만을 위한 일회성 시스템으로 고정하지 않는다.

태장 시스템을 첫 번째 실전 구현체로 삼되, 향후 업무수첩, 기관용 시스템, 신규 회사·조직, 별도 사내용 웹/앱 서비스에도 재사용할 수 있는 공통 업무플랫폼 기반으로 발전시키는 것을 장기 원칙으로 한다.

> 태장을 위해 개발하지만 태장에 종속되게 개발하지 않는다.

## 2. 현재 시스템은 계속 개발한다

이 원칙 때문에 현재 태장 홈페이지나 업무플랫폼 개발을 중단하거나 전면 재설계하지 않는다.

새 기능을 추가하거나 수정할 때마다 먼저 다음을 판단한다.

### A. 태장만의 업무인가?

예:

- 태장 직원 출퇴근
- 태장 공지사항
- 태장 고유 업무 프로세스
- 태장 내부 직원 역할
- 태장 회사 전용 메뉴

이 경우 **태장 Domain**에 둔다.

### B. 다른 서비스에서도 사용할 가능성이 높은가?

예:

- 로그인
- 사용자
- 조직
- 권한
- 알림
- 파일
- 검색
- 감사 로그
- API
- AI 처리
- 작업 큐
- 설정
- 앱 인증
- 푸시
- 공통 UI

공통성이 명확하면 가능한 한 **Platform / Shared / Core** 계층으로 분리한다.

## 3. 가장 중요한 구조 원칙

장기적으로 다음 구조를 지향한다.

```text
                 [ Platform / Core ]
                        │
       ┌────────────────┼────────────────┐
       │                │                │
      Auth            User           Organization
       │                │                │
 Notification         File            Search
       │                │                │
     Audit             AI             Jobs
       │
       └────────────────┬────────────────┘
                        │
          ┌─────────────┴─────────────┐
          │                           │
     [태장 Domain]               [업무수첩 Domain]
          │                           │
      Attendance                    Record
      Employee                      Schedule
      Notice                        Call
      태장 업무기능                  Meeting
                                    Scanner
```

태장 고유 기능과 공통 플랫폼 기능을 섞지 않는다.

## 4. 프론트엔드에도 같은 원칙을 적용한다

현재 태장 홈페이지의 프론트엔드는 향후 다른 홈페이지와 내부 서비스에서도 재사용할 수 있는 기반으로 발전시킨다.

공통 후보:

- 로그인 화면
- 전체 레이아웃
- 헤더
- 사이드 메뉴
- 모바일 UI
- 로딩 UI
- 에러 UI
- 모달
- 알림
- 사용자 메뉴
- 설정
- 파일 업로드
- 공통 폼
- 테이블
- 검색 UI
- 권한별 UI
- 공통 디자인 토큰

장기 구조:

```text
Web Foundation
     │
     ├── 태장 Web
     ├── 업무수첩 Web
     ├── 기관용 Web
     └── 향후 신규 서비스
```

단, 지금 당장 모든 UI를 공통 컴포넌트로 추출하지 않는다. 두 번째 사용처가 생기거나 공통성이 명확할 때 추출한다.

## 5. 백엔드는 태장이라는 이름에 종속시키지 않는다

공통 계층에서는 가능한 한 태장 전용 이름을 사용하지 않는다.

피해야 할 예:

- `taejangUser`
- `taejangNotification`
- `taejangFile`
- `taejangAuth`

공통 기능이면 다음과 같은 일반 개념을 우선한다.

- `User`
- `Organization`
- `Membership`
- `Notification`
- `File`
- `Auth`
- `Role`
- `Permission`
- `AuditLog`

반대로 실제 태장 전용 업무라면 태장 Domain에 명확히 둔다.

예:

- `Attendance`
- `EmployeeAttendancePolicy`
- `CompanyNotice`

## 6. Organization 개념을 중요하게 본다

향후 여러 회사·기관으로 확장할 가능성을 고려해 데이터 구조를 설계할 때 `Organization` 또는 이에 준하는 조직 경계를 고려한다.

장기적으로 다음 관계가 가능해야 한다.

```text
User
   │
Membership
   │
Organization
   │
   ├── 태장
   ├── 다른 회사
   └── 다른 기관
```

하지만 현재 태장 시스템에 필요하지 않은 복잡한 멀티테넌트 기능을 억지로 먼저 만들지 않는다. 현재 필요한 기능을 구현하되, 나중에 조직 개념을 넣기 어렵게 만드는 구조는 피한다.

## 7. 화이트라벨 가능성을 고려한다

향후 동일 기반에서 다른 회사용 서비스나 홈페이지를 만들 수 있도록 다음 항목은 가급적 설정 가능한 형태를 지향한다.

- 회사명
- 서비스명
- 로고
- 컬러
- 도메인
- 메뉴
- 권한
- 기능 활성화 여부
- 공지
- 앱 아이콘
- 푸시 설정

장기 목표:

```text
공통 Platform
+
회사별 설정
+
회사별 Domain
=
각 회사 서비스
```

## 8. 과도한 플랫폼화는 금지한다

현재 한 번만 사용되는 코드를 미래를 예상해서 무조건 추상화하지 않는다.

- 한 번 사용됨 → 태장 내부 코드로 두어도 된다.
- 두 곳 이상에서 동일한 구조가 필요해짐 → 공통화 여부를 검토한다.
- 앞으로 반복 사용될 것이 명확함 → 처음부터 공통 계층으로 설계한다.

> 복붙을 무조건 금지하지도 않고, 모든 것을 처음부터 플랫폼으로 만들지도 않는다.

실제 반복이 확인되면 공통화한다.

## 9. 기존 코드의 대규모 리팩터링은 별도 작업으로 한다

이 헌법을 적용한다고 해서 현재 정상 동작하는 태장 코드를 즉시 대규모로 이동하거나 리팩터링하지 않는다.

기본 전략:

```text
현재 정상 동작
      ↓
새 기능 개발
      ↓
공통성 판단
      ↓
경계 명확화
      ↓
필요할 때 공통 모듈 추출
      ↓
기존 코드 점진적 이전
```

전면 재작성보다 점진적 개선을 우선한다.

## 10. 저장소와 GitHub가 최종 기준이다

개발 관련 최종 사실은 채팅 기억보다 현재 GitHub `main`을 우선한다.

작업 시작 전에는 항상 다음을 확인한다.

1. 최신 `main` SHA
2. 현재 구현 상태
3. 관련 Issue / PR
4. 기존 공통 모듈 존재 여부

채팅에서 정한 중요한 구조와 개발 원칙은 가능한 한 GitHub 문서로 남긴다.

## 11. 이 문서를 상위 개발 원칙으로 보존한다

이 문서는 태장 시스템의 상위 아키텍처 원칙으로 취급한다.

새 기능이나 대규모 구조 변경 시 이 원칙과 충돌하는지 확인한다.

이 문서의 존재만으로 기존 정상 코드를 강제로 이동하거나 추상화하지 않는다.

## 12. 기능 개발 시 확인할 질문

새 기능을 만들 때 최소한 다음 질문을 확인한다.

1. 이 기능은 태장 전용인가?
2. 다른 회사나 업무수첩에서도 사용할 가능성이 있는가?
3. 데이터 구조가 태장이라는 회사명에 불필요하게 종속되어 있지는 않은가?
4. 프론트엔드 컴포넌트를 나중에 재사용할 수 있는가?
5. 인증·사용자·알림·파일·검색 같은 공통 기능을 중복 구현하고 있지는 않은가?
6. 지금 공통화해야 하는가, 아니면 두 번째 사용처가 생길 때까지 기다리는 것이 좋은가?
7. 현재 기능 구현 때문에 향후 다른 조직을 추가하기 어려운 구조가 되지는 않는가?

판단 결과는 필요한 경우 다음 중 하나로 명시한다.

- `태장 Domain`
- `Platform / Shared / Core`
- `현재는 태장에 두고 공통화 보류`

## 13. 장기 목표

태장 홈페이지와 업무플랫폼을 단순한 단일 회사 시스템이 아니라 공통 Work Platform의 첫 번째 구현체로 본다.

```text
                  Work Platform
                       │
        ┌──────────────┼──────────────┐
        │              │              │
       태장          업무수첩        기타 조직
        │              │              │
      Web/App         Web/App        Web/App
```

태장에서 검증된 공통 기능은 Platform으로 올리고, 태장만 필요한 업무 기능은 태장 Domain에 남긴다.

업무수첩이나 다른 서비스에서 검증된 공통 기능 역시 Platform으로 올릴 수 있다.

플랫폼은 태장에서 다른 서비스로 일방적으로 복사되는 구조가 아니라, 여러 실전 구현에서 검증된 좋은 기능이 공통 Platform으로 승격되는 구조를 지향한다.

## 14. 최우선 개발 원칙

앞으로의 개발에서 아래 두 문장을 최우선 원칙으로 사용한다.

> **현재 태장을 제대로 만드는 것을 우선한다. 그러나 태장만 만들 수 있는 구조로 만들지는 않는다.**

> **공통화가 명확한 것은 분리하고, 아직 명확하지 않은 것은 섣불리 추상화하지 않는다.**

이 두 원칙을 기준으로 개발을 진행한다.
